HTML 的非理性优势：
LLM 输出的范式转变

Anthropic Claude Code 团队的 Thariq Shihipar 发出了一个挑战传统认知的观点：当你向 LLM 请求输出时，应该要求 HTML 而非 Markdown。Simon Willison 回应说自己从 GPT-4 时代就默认用 Markdown，因为当时 8,192 token 的上下文窗口让 Markdown 的 token 效率极为重要——同样的内容，Markdown 比 HTML 节省大量 token。但时代变了。上下文窗口已经从 8K 膨胀到 200K 甚至更多，token 效率不再是瓶颈。而 HTML 能做到的事情远远超越 Markdown：SVG 图表、交互式组件、页内导航——这些让信息的呈现从「纯文本排版」跃升到「富交互体验」。

Thought-provoking piece by Thariq Shihipar (on the Claude Code team at Anthropic) advocating for HTML over Markdown as an output format to request from Claude.

I've been defaulting to asking for most things in Markdown since the GPT-4 days, when the 8,192 token limit meant that Markdown's token-efficiency over HTML was extremely worthwhile.

Thariq's piece here has caused me to reconsider that, especially for output. Asking Claude for an explanation in HTML means it can drop in SVG diagrams, interactive widgets, in-page navigation and all sorts of other neat ways of making the information more pleasant to navigate.

Markdown 时代：
8K token 下的生存法则

回到 2023 年，GPT-4 刚发布时只有 8,192 token 的上下文窗口。在这个极端稀缺的空间里，每一个 token 都是奢侈品。Markdown 的优势在于极致的 token 效率：一个一级标题 # Title 只需 3 个 token，而 HTML 的 <h1>Title</h1> 要 7 个 token 以上。段落文字不需要任何标签包裹，列表只需 - 开头，代码块用三个反引号就够了。因此在「上下文即黄金」的时代，Markdown 是理性的最优选择——它让模型把宝贵的 token 预算花在内容上，而非格式标签上。整个社区也因此形成了「Markdown 即标准输出格式」的惯性思维。

HTML 的三大超能力：
远超排版的表达空间

Markdown 本质上是一种排版语言——它能控制标题层级、粗体斜体、列表和代码块，仅此而已。但 HTML 是一种完整的文档编程语言，拥有三大 Markdown 无法企及的超能力。第一是 SVG 图表：LLM 可以在解释中直接嵌入矢量图，画出架构图、流程图、数据可视化，用图形传递文字难以表达的空间关系。第二是交互式组件：折叠面板、标签页、可展开的代码块、搜索过滤器——用户可以按需探索，而非被迫线性阅读。第三是页内导航：目录、锚点跳转、面包屑——让长文档不再是一滚到底的瀑布流，而是结构化的知识空间。

提示词的力量：
一句话改变输出维度

Thariq 分享了一个典型的 HTML 输出提示词：「帮我审查这个 PR，创建一个 HTML 页面来描述它。我不太熟悉 streaming/backpressure 的逻辑，所以重点关注这部分。渲染实际的 diff，用行内边注标注发现，按严重程度颜色编码，以及其他任何有助于传达概念的呈现方式。」这段提示词的关键不在于它要求了 HTML——而在于它释放了 LLM 的表达自由度。因为输出格式是 HTML，模型可以自主决定用什么视觉手法最适合传递信息：红色高亮严重问题、黄色标记警告、绿色表示建议，可折叠的代码块让审查者聚焦关键变更。如果输出是 Markdown，这一切都不可能。

150+ 单文件 HTML 工具
Simon 的工具哲学

Simon Willison 在两年内借助 LLM 创建了超过 150 个单文件 HTML 工具，托管在 tools.simonwillison.net 上。这些工具有四个共同特征：单文件（一个 .html 文件包含所有 HTML/CSS/JS）、无构建步骤（不用 React、不用 webpack、不用 npm install）、CDN 依赖（需要的库直接从 CDN 加载）、LLM 友好（几百行代码，LLM 能完整理解和修改）。这种模式的妙处在于它完美匹配 LLM 的能力边界——一个 HTML 文件就是一个自包含的应用，LLM 可以从零生成、完整理解、快速迭代。你不需要解释项目结构、不需要配置开发环境，只需要一句提示词。

实战：用 GPT-5.5 解释

四大原则：
单文件 · 无React · CDN · LLM友好

Simon 总结了高效 HTML 工具的四大原则。单文件意味着所有代码都在一个 .html 文件中，没有多文件依赖，可以随意复制和部署。无 React 不是偏见而是务实——React 需要构建步骤和复杂工具链，而原生 HTML/CSS/JS 加上 CDN 库足以应对绝大多数场景。提示词里加一句「No React」就能让 LLM 生成更简洁的代码。CDN 依赖意味着所有外部库通过 CDN URL 直接引入，不需要 npm install 或 node_modules。最后，LLM 友好是指工具代码控制在几百行以内，确保 LLM 能完整理解整个应用的上下文，从而实现「一次提示词 → 完整可用工具」的流程。这四个原则共同构成了 LLM 时代的前端开发范式。

状态管理：
URL vs localStorage

单文件 HTML 工具没有后端数据库，那状态存在哪里？Simon 提出两种互补的方案。URL 持久化把应用状态编码到 URL 参数中——比如他的 icon-editor 工具把整个图标设计状态存在 URL 里，用户分享链接就等于分享了完整的工作状态。这种方式天然支持书签和分享，缺点是 URL 长度有限制。localStorage 适合更大的状态和敏感数据（如 API 密钥）。word-counter 和 render-markdown 工具用 localStorage 自动保存用户输入，防止意外丢失。两种方案的共同点是：完全在浏览器端运行，不需要服务器，不需要用户注册账号。这正是单文件 HTML 工具的哲学——零摩擦。

URL-based persistence works well for shareable, bookmarkable applications. The icon-editor tool exemplifies storing substantial design state directly in URLs.

localStorage accommodates larger state and secrets like API keys without server exposure. Tools like word-counter and render-markdown use this pattern to auto-save work, preventing accidental data loss.

CORS API + 文件处理：
浏览器就是后端

单文件 HTML 工具不只是静态展示——它们可以直接调用外部 API 和处理本地文件。CORS 友好的 API 是关键资源：iNaturalist、PyPI、GitHub、Bluesky、Mastodon 都支持浏览器直接调用。GitHub 的公开仓库 API 特别好用，通过 raw.githubusercontent.com 访问的内容有 CDN 缓存，不用担心速率限制。OpenAI、Anthropic、Gemini 的 LLM API 也支持 CORS，结合 localStorage 存储 API 密钥就能在浏览器端直接调用大模型。文件处理方面，<input type="file"> 加上浏览器端库可以实现 OCR（Tesseract.js）、PDF 解析（PDF.js）等复杂功能，完全不需要上传到服务器。

CORS-enabled APIs unlock significant possibilities. Useful sources include iNaturalist, PyPI, GitHub, Bluesky, and Mastodon. GitHub's public repository API particularly shines, offering cached access via raw.githubusercontent.com without rate-limit anxiety.

LLM APIs (OpenAI, Anthropic, Gemini) support direct CORS calls, though API key management requires localStorage implementation for security.

File handling via input type="file" enables browser-based processing without server uploads. The OCR tool demonstrates running Tesseract.js and PDF.js locally.

Pyodide + WebAssembly：
Python 在浏览器中跑

HTML 工具的终极能力扩展来自 WebAssembly。Pyodide 把完整的 Python 运行时编译成 WASM，让 Python 代码直接在浏览器中执行——甚至支持通过 micropip 安装 PyPI 包。这意味着你可以在一个单文件 HTML 工具中运行数据科学工作流，不需要任何服务器端 Python 环境。更广泛地说，WebAssembly 把大量现有软件移植到了浏览器：Tesseract OCR 可以做文字识别，SLOCCount 可以统计代码行数。Simon 指出，这种「浏览器即平台」的模式避免了 LLM 平台沙盒的限制（比如 Claude Artifacts 不能加载外部数据、ChatGPT Canvas 会显示安全警告），同时 GitHub Pages 提供了免费、可靠的静态托管。
