Agentic 推理的秘密：
94% 的 token 都是重复的

随着 Claude Code、OpenClaw 等 LLM agent 的兴起，推理工作负载正在发生根本性变化。Agent 的执行模式是长周期的多轮循环——交替进行推理步骤（处理上下文、产生中间思考）和行动步骤（调用工具、接收外部输出）。vLLM 团队分析了 Codex 在 SWE-bench Pro 上的 610 条 trace 后发现了一个惊人的模式：到第 30 轮时，上下文长度增长到约 80K token，但每轮只新增几百到几千个 token，其余全是模型已经见过的前缀。整个数据集的平均输入输出比是 131:1。Cache 命中率高达 94.2%。如果能缓存这些前缀，那么缓存部分的 prefill 基本免费——每轮的真实计算成本只有新增的那一小部分 delta。

The pattern is striking: by turn 30, context length grows to roughly 80K tokens, and the longest contexts can grow beyond 180K tokens. Yet each turn typically introduces only a few hundred to a few thousand new tokens. The rest is prefix that the model has already seen. Across the dataset, the average input-to-output token ratio is roughly 131:1.

If we can cache those prefixes, prefill for the cached portion becomes essentially free. The true per-turn cost is only the new delta.

Across the Codex/SWE-bench Pro dataset, comprising 610 traces with a median of 33 turns per trace, we observe: 94.2% cache hit rate, 131:1 input-to-output ratio, Average context growth of roughly 2,242 tokens per turn, Median context growth from 12K to 80K tokens per trace.

本地 KV Cache 撑不住
Agentic 工作负载

虽然 94% 的 token 理论上可以缓存，但本地 KV cache 卸载到 CPU DRAM 或磁盘面临两大致命瓶颈。第一个是容量饱和与驱逐：一个 100K token 的上下文占用 GB 级存储（比如 Kimi-2.5 FP8 KV cache 约 3.8 GB），繁忙实例上的多个长会话会迅速撑满本地容量并触发驱逐。第二个是跨实例 Cache Miss：为了负载均衡，路由器不总是把同一会话的下一轮调度到同一个 vLLM 实例，如果会话被迁移到另一个实例，那个实例从未见过这个前缀，必须从头重算。结论：我们不能再把推理服务视为一组孤立的 vLLM 副本——agent 工作负载需要一个分布式 KV cache 池。

Mooncake Store：
跨节点共享的 KV Cache 池

Mooncake 是一个开源的高性能 KV cache 传输和分布式存储库。vLLM 已经通过 MooncakeConnector 集成了 Mooncake 的传输引擎用于 prefill-decode 解耦。现在更进一步：用 Mooncake Store 构建分布式 KV cache 池。架构分两部分：Master 服务器在集群范围运行，管理元数据（KV block 哈希、大小等）、监控客户端健康、提供服务发现和死节点清理；Client 运行在 GPU 节点上，管理本地 CPU/DRAM/SSD 资源，客户端之间通过 RDMA 传输 KV cache，共同组成分布式池。vLLM 的集成插入现有的 KVConnector 接口——调度器侧查询 master 获取匹配的 KV block 来指导调度决策，工作者侧在每个 GPU worker 中嵌入 Mooncake client 并启动后台线程做数据搬运。

Mooncake is an open-source, high-performance library for KV cache transfer and distributed storage. vLLM has already adopted Mooncake for prefill-decode (PD) disaggregation via the MooncakeConnector, using Mooncake's transfer engine to move KV caches between GPUs. Now, we take that integration one step further by building a distributed KV cache pool with Mooncake Store.

At a high level, Mooncake Store offers a master server and a set of clients. The master server runs cluster-wide and manages metadata, including KV block hashes, sizes, etc. It also monitors client health and availability, providing service discovery and dead-node cleanup.

Mooncake clients run on GPU nodes where they manage local CPU/DRAM/SSD resources. Clients connect to one another through RDMA for KV cache transfer. Together, they form a distributed KV cache pool.

零拷贝 + 全异步：
不占 GPU 算力的 KV 传输

KV cache 传输的关键设计挑战是不能干扰 GPU 上的推理计算。传统方法要么用 cudaMemcpyAsync（GPU 拷贝引擎，小块传输效率低），要么用 GPU kernel（用 SM 拷贝数据，会干扰其他 kernel）。vLLM + Mooncake 采用第三条路：GPUDirect RDMA——用 RDMA 网卡直接在 GPU HBM 和 CPU 内存之间搬运 KV block，不需要中转缓冲区，不消耗 SM。Mooncake Transfer Engine 还支持多网卡池化和拓扑感知路径选择，聚合利用所有 RNIC 的带宽。所有 RDMA 操作都在专用后台 I/O 线程上运行，从 vLLM 视角看传输路径是完全异步的，不会阻塞主 CPU 路径。

GPUDirect RDMA 和 MultiConnector 的技术细节是什么？

3.8x 吞吐 · 46x TTFT · 8.6x 延迟

在真实的 Codex agentic trace 上测试（1P1D 配置，12 个 GB200 GPU，Kimi-2.5 NVFP4 模型），分布式 KV cache 池把 vLLM 的吞吐提升了 3.8 倍，P50 TTFT（首 token 延迟）降低了 46 倍，端到端延迟降低了 8.6 倍。这些巨大收益的驱动力是 cache 命中率的戏剧性提升：从 1.7%（只缓存 system prompt）飙升到 92.2%（几乎整个前缀都被缓存）。这意味着在 agentic 场景下，绝大部分 prefill 计算被完全跳过了——模型只需要处理每轮新增的那一小段 delta。

The distributed KV cache pool improves vLLM throughput by 3.8x and reduces P50 TTFT and E2E latency by 46x and 8.6x, respectively. These gains are driven by a dramatic increase in cache hit rate: from 1.7%, where only the system prompt is cached, to 92.2%, where nearly the entire prefix is cached.

To stress-test the datapath under cross-node traffic, we used round-robin routing. As a result, requests could be scheduled on different nodes across turns and often needed to fetch KV caches from a previous node.

100K token = 3.8 GB
本地内存根本装不下

容量饱和是本地 KV cache 的第一个致命问题。以 Kimi-2.5 的 FP8 KV cache 为例，一个 100K token 的上下文就占用约 3.8 GB 存储。在繁忙的实例上，同时服务多个长会话时，这些大型前缀缓存会迅速撑满本地 CPU DRAM 或磁盘容量。一旦容量满了，旧的缓存就会被驱逐——而被驱逐的恰恰可能是当前活跃会话的前缀。下一轮到来时，系统不得不从头重新计算整个前缀，浪费大量 prefill 计算。这本质上是一个存储容量和会话数量之间的矛盾：agent 会话越长、并发越多，本地容量就越不够用。

换了节点？
前缀全部重算

跨实例 Cache Miss 是第二个致命问题。为了负载均衡，路由器不总是把同一个会话的下一轮调度到同一个 vLLM 实例。当会话被迁移到另一个实例时，那个实例从未见过这个会话的前缀，必须从头重新计算——即使前一个实例的本地缓存里还完整保存着这个前缀。在 agentic 场景下，一个 80K token 的前缀被强制重算的代价是巨大的，而这种情况在集群规模增长时会越来越频繁。这就是为什么团队得出结论：推理服务不能再是一组孤立的副本，agent 工作负载需要实例之间能共享 KV cache。

GPUDirect RDMA：
不用 SM，不用中转

传统 GPU-CPU 数据传输有两种方式：cudaMemcpyAsync（用 GPU 拷贝引擎，但对很多小块传输效率低）和 GPU kernel 拷贝（用 SM，能处理大量小块但会干扰其他 kernel）。vLLM + Mooncake 选择了第三条路：GPUDirect RDMA——用 RDMA 网卡直接在 GPU HBM 和 CPU 内存之间搬运 KV block。GPU 的 KV cache 内存被注册为 RDMA buffer，实现 GPUDirect RDMA 读写，不需要中转缓冲区，不消耗任何 SM。Mooncake Transfer Engine 还通过多网卡池化（multi-NIC pooling）和拓扑感知路径选择来聚合利用节点上所有 RNIC 的网络带宽。这意味着 KV cache 传输完全在「推理计算路径之外」进行，不会对模型推理造成任何干扰。

We take a third approach: using the RDMA NIC and GPUDirect RDMA to move KV blocks directly between GPU HBM and CPU memory. This path requires no staging buffer and does not consume SMs. It also performs well for large numbers of small KV block transfers.

Thanks to the Mooncake Transfer Engine, the transfer path can also leverage multiple RNICs on a node through multi-NIC pooling and topology-aware path selection. This allows KV transfers to aggregate and better utilize available network bandwidth across NICs.

MultiConnector：
PD 解耦 + 分布式池一起用

通过 MultiConnector 接口，vLLM 可以同时启用 PD（prefill-decode）解耦和分布式 KV cache 池。MultiConnector 是一个包装器，把多个子 connector 串联起来，每个独立运行。在 prefill 侧：prefill 实例为 PD connector 准备 KV block，同时通过 store connector 把它们存入分布式池。对于 cache 命中，vLLM 查询所有 connector 并从 Mooncake Store 恢复匹配的前缀。在 decode 侧：decode 实例写入分布式池的 KV block 立即对 prefill 实例可见。因为 vLLM 把每个请求同时调度到 prefill 和 decode 实例，prefill 实例从池中加载前缀 KV block 后通过 PD connector 转发给 decode。团队正在开发从 prefill 实例和分布式池的多路径同时加载，以最大化可用网络带宽。

The integration also naturally extends to PD disaggregation through the MultiConnector interface. MultiConnector is a wrapper that chains multiple sub-connectors together. Each connector operates independently and does not rely on the others.

Prefill: The prefill instance prepares KV blocks for the PD connector and also stores them in the distributed KV cache pool through the store connector. For cache hits, vLLM queries all connectors and can recover matching prefixes from the Mooncake Store connector.

Decode: When the decode instance writes KV blocks into the distributed pool, they immediately become visible to prefill instances.
