01 - 代码规模爆炸
LLM 生成了 14 万行的编译器

LLM 辅助开发已经非常普遍，甚至可以生成超过 10 万行代码的大型系统——编译器、深度学习框架、操作系统。但由于 LLM 的幻觉问题，生成的代码可能包含 bug。对这些大规模系统进行正确性验证变得至关重要，然而现有的自动化验证技术在面对大规模系统时力不从心——系统代码结合了复杂的控制流、丰富的状态操作和深层的函数间依赖。

02 - 理论完美，实践卡住
{P} C {Q} 能证明代码正确
但谁来写 14 万行的规约？
组合推理是一个很有前景的方法——对每个小组件单独推理，然后组合起来证明整个系统的正确性。Hoare 逻辑用三元组 {P} C {Q} 来定义代码片段的形式化规约：P 是执行前必须满足的前置条件，Q 是执行后保证成立的后置条件。但关键瓶颈在于：Hoare 逻辑要求为每个函数写形式化规约，这需要大量人力。对于 LLM 生成的代码，开发者往往对代码缺乏深入理解，写规约更是难上加难。

03 - 核心洞察
不看代码怎么写的
看调用者怎么用的
FM-Agent 的核心洞察：从调用者推导规约比从实现推导更准确。传统方法从函数实现推导规约，但如果实现本身有 bug，推导出的规约就会把 bug 当作正确行为。FM-Agent 反过来看——分析调用者如何使用这个函数，从调用者的期望推导出函数应该做什么。调用者传入的参数可以帮助推断前置条件，调用后的后续代码可以帮助推断后置条件。而且 LLM 能准确预测小代码块的执行结果——在微软 VerusBench 上，Claude Code 对 98.6% 的函数正确预测了执行结果。

04 - 三大组件
生成规约 → 推理验证 → 触发 bug
三个核心组件组成流水线：规约生成器采用自顶向下方式，从入口函数开始沿调用图逐层向下生成规约，同一层的函数并行处理以提升可扩展性。代码推理器推广了 Hoare 逻辑的推理规则，使其能处理自然语言的前后置条件——从函数的前置条件开始，逐语句推导后置条件，如果最终无法蕴含规约中的后置条件，则报告潜在 bug。Bug 验证器为每个潜在 bug 生成系统级测试用例来触发它，最多尝试 10 次。

05 - 实战结果
2 天处理 27.7 万行代码
发现 522 个新 bug
FM-Agent 在 4 个大规模系统上进行了评估：CCC 编译器（143k 行，339 个 bug）、VibeTensor 深度学习框架（108k 行，141 个 bug）、VibeOS 操作系统（15k 行，23 个 bug）、Bespoke OLAP 数据库（11k 行，19 个 bug）。这些系统已经被开发者用各种方法测试过——单元测试、集成测试、差分测试、多 agent code review——但 FM-Agent 仍然发现了 522 个新 bug。消融实验更能说明问题：去掉自顶向下的规约生成后，在 CCC 上只发现 57 个 bug（vs 339 个）。整个推理过程总计消耗 34 亿 token。
