你的 multi-agent 工作流跑完了，每个 agent 都在行动——但结果是一团糟

如果你搭建过 multi-agent 工作流，大概率见过这种诡异的失败方式：系统跑完了，agent 们也确实采取了行动，但某个地方悄悄出了问题——一个 agent 关掉了另一个 agent 刚打开的 issue，或者提交了一个会让下游检查失败的变更。之所以会这样，是因为当多个 agent 开始处理相关任务——分类 issue、提交变更、运行检查、开 PR——它们就开始对状态、顺序和验证做出隐式假设。如果你不提供明确的指令、数据格式和接口，事情就不会按你计划的走。GitHub 团队在构建 Copilot、内部自动化和 multi-agent 编排的过程中发现，multi-agent 系统的行为更像分布式系统，而不是聊天界面。

Original

If you've built a multi-agent workflow, you've probably seen it fail in a way that's hard to explain.

The system completes, and agents take actions. But somewhere along the way, something subtle goes wrong. You might see an agent close an issue that another agent just opened, or ship a change that fails a downstream check it didn't know existed.

That's because the moment agents begin handling related tasks—triaging issues, proposing changes, running checks, and opening pull requests—they start making implicit assumptions about state, ordering, and validation. Without providing explicit instructions, data formats, and interfaces, things won't go the way you planned.

Through our work on agentic experiences at GitHub across GitHub Copilot, internal automations, and emerging multi-agent orchestration patterns, we've seen multi-agent systems behave much less like chat interfaces and much more like distributed systems.

单个 agent 不够用时，团队引入多个 agent——同时也引入了新的失败面

团队之所以使用 multi-agent 工作流，是因为单个 agent 无法可靠地端到端解决问题。但引入多个 agent 也同时引入了新的失败面：共享状态、顺序假设、隐式交接和非确定性行为。开发者通常把 multi-agent 用在代码库维护和依赖更新、自动化代码质量检查和重构、基于 spec 的功能实现、以及 issue 和 PR 分类这些场景上。但这些场景只有在每一步都显式且受约束的情况下才能可靠运行。文章接下来介绍了三个让 agent 系统变可靠的工程模式。

ACT II · 三个工程模式

自然语言是混乱的。Typed Schema 让数据传递变可靠

Multi-agent 工作流经常在早期就失败，原因是 agent 之间交换的是混乱的自然语言或不一致的 JSON——字段名变了、数据类型不匹配、格式漂移，而且没有任何机制来强制一致性。这就好比软件开发中尽早建立契约（contract）能帮助团队协作而不互相踩脚一样，类型化接口和严格的 schema 在每个边界上都添加了结构。Agent 传递的是机器可检查的数据，无效消息会快速失败，下游步骤不需要猜测 payload 的含义。大多数团队从定义期望 agent 返回的数据形状开始——比如一个 TypeScript 类型声明。这样一来，调试就从「检查日志然后猜」变成了「这个 payload 违反了 schema X」。

Original

Multi-agent workflows often fail early because agents exchange messy language or inconsistent JSON. Field names change, data types don't match, formatting shifts, and nothing enforces consistency.

Just like establishing contracts early in development helps teams collaborate without stepping on each other, typed interfaces and strict schemas add structure at every boundary. Agents pass machine-checkable data, invalid messages fail fast, and downstream steps don't have to guess what a payload means.

Most teams start by defining the data shape they expect agents to return: type UserProfile = { id: number; email: string; plan: "free" | "pro" | "enterprise"; };

This changes debugging from "inspect logs and guess" to "this payload violated schema X." Treat schema violations like contract failures: retry, repair, or escalate before bad state propagates.

模糊的意图让 agent 崩溃。Action Schema 让意图变明确

即使有了类型化数据，multi-agent 工作流仍然会失败，因为 LLM 不会遵循隐含的意图——它们只遵循明确的指令。「分析这个 issue 并帮团队采取行动」听起来很清楚，但不同的 agent 可能会关闭、分配、升级或什么都不做——每种行为都合理，但没有一种是可自动化的。Action Schema 通过定义允许的动作集合及其结构来解决这个问题。不是每一步都需要结构，但结果必须始终解析为一个小的、明确的动作集合。有了 Action Schema，agent 必须返回恰好一个有效动作——任何其他输出都会验证失败并被重试或上报。

Original

Even with typed data, multi-agent workflows still fail because LLMs don't follow implied intent, only explicit instructions.

"Analyze this issue and help the team take action" sounds clear. But different agents may close, assign, escalate, or do nothing—each reasonable, none automatable.

Action schemas fix this by defining the exact set of allowed actions and their structure. Not every step needs structure, but the outcome must always resolve to a small, explicit set of actions.

Here's what an action schema might look like: const ActionSchema = z.discriminatedUnion("type", [ { type: "request-more-info", missing: string[] }, { type: "assign", assignee: string }, { type: "close-as-duplicate", duplicateOf: number }, { type: "no-action" } ]);

With this in place, agents must return exactly one valid action. Anything else fails validation and is retried or escalated.

Schema 定义结构，Action Schema 定义意图。MCP 强制执行两者

类型化 schema、受约束的动作和结构化推理，只有在被一致地强制执行时才有效。如果没有执行机制，它们就只是约定，而不是保证。Model Context Protocol（MCP）就是把这些模式变成契约的执行层。MCP 为每个工具和资源定义了明确的输入和输出 schema，在执行前就进行校验。有了 MCP，agent 就不能凭空发明字段、省略必需输入、或在接口间漂移。验证发生在执行之前，从而防止坏状态到达生产系统。

Typed schemas, constrained actions, and structured reasoning only work if they're consistently enforced. Without enforcement, they're conventions, not guarantees.

Model Context Protocol (MCP) is the enforcement layer that turns these patterns into contracts.

MCP defines explicit input and output schemas for every tool and resource, validating calls before execution.

With MCP, agents can't invent fields, omit required inputs, or drift across interfaces. Validation happens before execution, which prevents bad state from ever reaching production systems.

ACT III · 设计原则

把 agent 当代码来对待，而不是聊天界面

基于 GitHub 构建和运维 agentic 系统的经验，文章总结了让 multi-agent 工作流在规模化时可靠运行的设计原则：首先是设计时先考虑失败——因为 agent 会失败，就像分布式系统中的节点会失败一样；然后是验证每个 agent 边界——每次数据交接都需要校验；接着是在添加更多 agent 之前先约束动作——问题通常不是 agent 不够多，而是约束不够强；还要记录中间状态、预期重试和部分失败。最后也是最核心的一条：把 agent 当作分布式系统来对待，而不是聊天流。当你加上 typed schema、受约束的 action 和 MCP 强制执行的结构化接口时，agent 就开始像可靠的系统组件一样运行了。

Based on our experience building and operating agentic systems at GitHub, these principles help make multi-agent workflows reliable at scale: Design for failure first Validate every agent boundary Constrain actions before adding more agents Log intermediate state Expect retries and partial failures Treat agents like distributed systems, not chat flows

Multi-agent systems work when structure is explicit. When you add typed schemas, constrained actions, and structured interfaces enforced by MCP, agents start behaving like reliable system components.

The shift is simple but powerful: treat agents like code, not chat interfaces.

Schema 违规 = 契约失败：重试、修复、或上报

文章强调应该把 schema 违规当作契约失败来处理——在坏状态传播之前就要重试、修复或上报。具体来说，大多数团队从定义期望 agent 返回的数据形状开始，比如一个 TypeScript 类型声明，明确规定每个字段的名称、类型和允许的值域。当一个 agent 的输出不符合 schema 时，系统不应该继续执行，而应该立即触发验证失败。这把调试从「检查日志然后猜测哪里出了问题」变成了「这个 payload 违反了 schema X 的字段 Y」——精确且可追溯。这种模式之所以有效，是因为它在每个 agent 边界上都添加了结构，让 agent 传递的是机器可检查的数据，而不是自由格式的自然语言。

MCP：在执行前校验每一次工具调用的输入和输出

MCP 为每个工具定义了明确的 input_schema 和 output_schema。当 agent 要调用一个工具时，MCP 会在执行前校验调用参数是否符合 input_schema——如果 agent 凭空发明了一个字段、省略了必需参数、或类型不匹配，调用会被拒绝，根本不会到达目标系统。同样地，工具返回的结果也会被 output_schema 校验。这样一来，schema 定义的是数据结构，action schema 定义的是允许的意图，而 MCP 在运行时强制执行两者。没有 MCP，schema 和 action schema 只是约定——开发者可以遵守也可以不遵守；有了 MCP，它们变成了编译时检查一样的硬性保证，坏状态永远不会到达生产系统。
