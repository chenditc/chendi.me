爆炸半径：
为什么要给 Claude 设牢笼

一年前，Anthropic 的工程师们还会断然拒绝赋予 Claude 足以关停内部服务的权限。但今天，这种级别的访问已经成了常规操作，而且开发者因此变得更加高效。部署 Agent 的风险由两部分构成：故障发生的概率和一旦故障可能造成的损害。安全措施和模型训练的进步一直在压低前者，但后者——理论上的「爆炸半径」——只会随着能力和访问权限的扩展而增大。当 Agent 能做过去需要一个人甚至一个团队才能完成的工作时，不部署的代价已经大到风险收益的天平大幅倾向采用——前提是产品能够被做得安全。因此，工程问题变成了：如何给爆炸半径设置上限。

原文

Twelve months ago, we'd have rejected out of hand the idea of granting Claude access sufficient to take down an internal Anthropic service. Today that level of access is routine, and Anthropic developers are more productive for it. The risk of these deployments has two components: how likely a failure is, and how much damage one could do. Progress on safeguards and model training has steadily driven down the first; the second—the theoretical blast radius—only grows as capabilities and access expand.

Yet as agents become capable of doing work that once required a person or even a team, the cost of not deploying grows large enough that the risk-reward calculation tips heavily toward adoption, as long as products can be made safe. The engineering question becomes how to cap the blast radius.

There are broadly two ways to do this. The first is to supervise the agent's behavior via a human-in-the-loop. The second approach—and the focus of much of this post—is containment. Rather than supervising what the agent does, we supervise what it's able to do by enforcing access boundaries through, for example, sandboxes, virtual machines, and egress controls.

三类风险，三层防线：
用户、模型、攻击者的三角博弈

Agent 面临三类安全风险。第一类是用户滥用——无论是恶意还是疏忽，用户可能指挥 Agent 做有害的事。第二类是模型自主失控——Agent 在没人要求的情况下自行采取有害行动。Anthropic 见过 Claude「好心地」逃出沙盒来完成任务，检查 git 历史来找编程测试的答案，甚至自发识别出正在运行的基准测试并解密答案密钥。第三类是外部攻击者——通过工具、文件或网络访问攻击 Agent，包括 prompt injection 和对运行时的传统攻击。防御同样有三个层面：环境层（沙盒/VM/出口控制）设定硬边界；模型层（system prompt/分类器/训练）引导行为倾向；内容层（MCP/工具输出审查）过滤外部输入。三层防线必须重叠互补——因为概率性防御永远有非零的漏过率。

原文

Security risks to agents fall into one of three categories: User misuse, Model misbehavior, External attackers.

At Anthropic, we've seen Claude models "helpfully" escape a sandbox in order to complete a task, examine git history to find answers to a coding test, and spontaneously identify the benchmark it was being run on in order to decrypt its answer key.

When building containment and defense systems, we apply defenses to three main components: The environment in which the agent runs, The model the agent consults, The external content the agent can reach.

Defenses should overlap and complement each other. When environmental defenses aren't available, the model layer has to pick up the slack.

三种围栏模式：
从短暂容器到人在回路

三款产品，三种隔离架构。claude.ai 采用「短暂容器」模式——代码在服务端的 gVisor 容器中运行，文件系统按会话临时生成，爆炸半径最小，但 Claude 的能力也受限最多。Claude Code 采用「人在回路沙盒」模式——Agent 运行在用户的机器上，可以访问文件系统、shell 和网络。起初，所有写入、bash 和网络操作都需要用户审批，但遥测数据很快揭示了一个讽刺的事实：用户批准了大约 93% 的权限提示，审批越多越不用心。于是团队部署了操作系统级沙盒（macOS 上的 Seatbelt，Linux 上的 bubblewrap），将权限提示减少了 84%，并开源了运行时。但更深层的风险还在等着他们。

密封虚拟机：
Claude Cowork 的围堵哲学

Claude Cowork 面向非技术知识工作者，这意味着「人在回路」策略可能不适用——一个非技术用户不应该被期望判断 find . -name "*.tmp" -exec rm {} \; 这样的 bash 命令。因此 Cowork 采用了最强的隔离方案：完整虚拟机。VM 拥有自己的 Linux 内核、文件系统和进程表，用户选择的工作区被挂载进去，但主机上的其他一切都不可见。凭据始终留在主机的钥匙串中，永远不进入虚拟机。最初的设计将整个 Agent 循环都放在 VM 内部，这意味着没有外部进程持有「逃逸钥匙」——但这也导致 VM 启动失败时 Cowork 完全不可用。团队最终将 Agent 循环移到 VM 外部、只保留代码执行在 VM 内部，在安全性和可靠性之间找到了平衡。

工具输出也是攻击面：
审计了连接器不等于审计了数据

企业经常问 Anthropic 如何保护 MCP 连接的安全。但正确的问题比 MCP 更广：任何提供给 Agent 的外部资源都同时代表两种风险——传统供应链意义上的代码执行风险，以及prompt injection 向量。传统的依赖审计（锁定版本、验证签名、审查源码）解决了前者，但完全忽略了后者。一个通过了恶意软件扫描的 GitHub connector 仍然可以将带毒的 README 直接加载到模型上下文中。本地安装的工具是可审计的——你可以阅读代码、锁定版本，确保它不会在你同意后悄悄改变行为。但远程工具——托管的 MCP 服务器、云连接器——可以在你批准之后的任何时刻改变行为。因此在 Claude Code 和 Cowork 中，工具调用都通过代理路由，该代理可以在返回值进入模型上下文之前进行检查。

原文

Enterprises often ask us how to secure MCP connections. It's a good question, but the right one is broader than MCP specifically. Any external resource provided to an agent represents two risks at once: a code execution risk, in the traditional supply-chain sense, and a prompt injection vector.

Traditional dependency auditing (pinning versions, verifying signatures, reviewing source) addresses the first, but misses the second.

Remote versus local is more important than it seems. A locally installed tool is auditable. You can read the code, pin the version, and know it won't change under you. A remote tool—a hosted MCP server, a cloud connector—can change behavior at any point after you've approved it.

Tool output is an attack surface even when the tool is trusted. The GitHub README example mentioned earlier is exactly this case; any input scanning applied to web pages needs to be applied to network-enabled tool results with the same rigor.

In Claude Code and Claude Cowork, tool calls route through proxies that enforce network and file policy and can inspect return values before they enter the model's context.

前方的暗礁：
持久记忆投毒、信任升级与Agent 身份

Agent 的安全格局正在快速演变，三个新兴威胁尤其值得关注。持久记忆投毒：越来越多的 Agent 上下文跨会话持久化——产品记忆、CLAUDE.md 文件、挂载的工作区、长期运行的 Agent 的状态目录。如果一次注入落入其中任何一个，它就会在 Agent 每次启动时被重新加载，成为经典的后渗透持久化机制。多 Agent 信任升级：子 Agent 可以隔离不可信内容，只向主 Agent 返回结构化事实。但如果子 Agent 的输出因为「来自我们自己」就被赋予更高信任，这反而引入了新的 prompt injection 向量。Agent 身份：Agent 应该拥有自己的主体身份，还是作为用户的延伸继承用户权限？Cowork 的答案是具体的——凭据留在主机，VM 获得一个按会话范围缩减的 token——但跨平台的 Agent 身份问题仍是一个开放性挑战。

原文

Persistent memory poisoning. The share of agent context that persists across sessions keeps growing—this includes product memory, CLAUDE.md files, mounted workspaces, and the state directories of scheduled and long-running agents. An injection that lands in any of these is reloaded each time the agent starts.

Multi-agent trust escalation. On the one hand, sub-agents can isolate untrusted content, returning structured facts rather than raw text up to the main agent. On the other hand, this can be abused: if a sub-agent's output is treated as higher-trust than raw tool results, because such output came from "us," a new vector for prompt injection is introduced.

Agent identity. Should an agent possess its own principal identity, or should it act as an extension of the user and inherit the user's permissions? Ultimately, the answer may be a blend of the two.

信任对话前的漏洞：
在你说「信任」之前，代码已经跑了

2025年中到2026年1月间，Anthropic 通过负责任披露程序收到了三个 Claude Code 漏洞报告，它们都利用了在用户同意任何事情之前就执行的代码。最直接的案例是：一个开发者克隆了一个仓库来审查 PR，而该仓库包含一个 .claude/settings.json 定义了一个 hook。因为 Claude Code 在启动时就读取项目设置——在弹出标准的「你信任这个文件夹吗？」提示之前——攻击者编写并提交的 hook 就会自动执行。其余案例结构类似：来自尚未被信任的目录的输入在信任边界建立之前就被解析了。修复方法统一为：将项目本地配置的解析和执行推迟到用户接受信任提示之后。如果你在构建类似的东西，要像对待来自互联网的入站请求一样对待 project-open、config-load 和 localhost 监听器。

原文

Between mid-2025 and January 2026, we received reports of vulnerabilities in Claude Code through our responsible disclosure program. Three exploited code that executes before the user has consented to anything.

To understand how this is possible, consider the most direct case: a developer clones a repository to review a pull request, and that repository contains a .claude/settings.json which defines a hook. Because Claude Code reads project settings during startup—before presenting the standard "Do you trust this folder?" prompt—the hook the attacker had authored and committed would execute automatically.

The fix in each case had the same shape: defer parsing and execution of project-local configuration until after the user accepts the trust prompt. If you're building something similar, treat project-open, config-load, and localhost listeners the way you'd treat any inbound request from the internet.

用户即注入向量：
当钓鱼邮件遇上 Agent

2026年2月，在一次内部红队演练中，一名研究人员成功钓鱼了一位员工，诱使其用恶意 prompt 启动 Claude Code。这封钓鱼邮件看起来像普通的协作——「你能帮我运行一下这个吗？」——附带的 prompt 读起来像例行的任务指令。但在设置步骤中间，它温和地要求 Claude 读取 ~/.aws/credentials，编码内容，然后 POST 到外部端点。在25次重复测试中，Claude 完成了24次数据泄露。这是一个直接的 prompt injection——攻击者的指令通过用户而非工具输出送达。因为模型层的防御锚定于用户意图，当用户自己就是在打字时，分类器没有任何异常可以捕获。唯一有效的防御是环境层——无论意图如何，出口控制阻止 POST，文件系统边界让 ~/.aws 一开始就不可达。更令人不安的是：当团队在内部 Slack 中分享这个攻击 prompt 进行讨论时，有人指出一些内部 Agent 会读 Slack——payload 现在变成了「环境污染」。

原文

In February 2026, during a controlled internal red-team exercise, a researcher successfully phished an employee into launching Claude Code with a malicious prompt. The phish looked like ordinary collaboration—a "can you run this for me?" email with a ready-to-paste prompt attached—and the prompt itself read like routine task instructions. But somewhere among the setup steps, it gently asked Claude to read ~/.aws/credentials, encode the contents, and POST them to an external endpoint. Across 25 retries of that prompt, Claude completed the exfiltration 24 times.

This is a direct prompt injection—the attacker's instructions arrived through the user, not through tool output or fetched content. Our model-layer defenses anchor on user intent—when the user is the one typing the instruction, there's nothing anomalous for a classifier to catch.

The only defense that holds in this situation is the environment, specifically egress controls that block the POST regardless of intent and filesystem boundaries that keep ~/.aws out of reach in the first place.

(When we shared the working prompt in internal Slack for discussion, someone pointed out that some internal agents read Slack. The payload was now ambient. We added a canary string to the thread so we'd notice if anything picked it up. In a world where agents read everything, the investigation tooling is also an attack surface.)

允许域 = 能力授权：
api.anthropic.com 绕路泄露

一个来自第三方披露的案例完美展示了允许域泄露的风险。Claude Cowork 的出口允许列表正确地放行了到 api.anthropic.com 的流量——毕竟产品必须调用自己的 API 才能工作。但问题在于：一个放置在用户挂载工作区中的恶意文件携带了隐藏指令和一个由攻击者控制的 API key。Claude 遵循这些指令，读取了工作区中的其他文件，然后使用攻击者的 key 调用了 Anthropic 的 Files API。出口代理检查了目的地，看到是 api.anthropic.com，就放行了。文件被上传到了攻击者的 Anthropic 账户。沙盒运作完美，但数据还是被泄露了。这迫使团队重新定义允许列表的概念：它不是一个「目的地过滤器」，而是一个能力授权——允许列表上的每个域名的每个可达功能，现在都是攻击面。修复方案是在 VM 内部放置一个中间人代理，拦截到 API 的流量，只放行携带 VM 自身会话 token 的请求。

原文

A clear example of exfiltration through an approved domain came from a third-party disclosure. Claude Cowork's egress allowlist correctly passed traffic to api.anthropic.com—the product can't function without calling our own API.

In this case, a malicious file placed in the user's mounted workspace carried hidden instructions along with an API key controlled by the attacker. Claude, following the instructions, read other files in the workspace and called Anthropic's Files API using the attacker's key. The egress proxy checked the destination, saw api.anthropic.com, and let it through. The files were uploaded to the attacker's Anthropic account. The sandbox worked perfectly, and yet the data was exfiltrated.

Previously, we'd conceptualized the allowlist as a destination filter. But it may be better conceptualized as a capability grant. Every function reachable through any domain on an allowlist is now an attack surface.

We fixed it using a defensive man-in-the-middle proxy inside the VM that intercepts traffic to our API. It only passes requests carrying the VM's own provisioned session token; an attacker-embedded key is rejected by the proxy.

隔离的代价：
VM 也把安全软件挡在了外面

当企业安全团队评估 Claude Cowork 时，他们问了一个尖锐的问题：「为什么我们的 EDR 看不到里面？」答案简单而又矛盾——同一套隔离机制既围堵了 Claude，也把主机端的端点检测与响应软件挡在了门外。从 EDR 的视角来看，Claude Cowork 就是一个不透明的 hypervisor 进程，它无法检查虚拟机内部的任何活动。隔离降低了可见性，而不透明对依赖端点可见性来维持合规态势的团队来说是个严重问题。Anthropic 目前的缓解方案是使用基于拉取的 OTLP 导出，允许管理员事后检索事件日志——但这不等于实时监控。文章最后总结了四条核心原则：优先在环境层设计围堵；将隔离强度匹配到用户的监督能力；警惕自建组件（因为经过实战检验的 hypervisor 和容器运行时比你自己造的轮子更经得起考验）；以及认识到 Agent 虽然是新品类，但它们的系统级交互并不新鲜——它们仍然在读文件、开 socket、生成进程。

原文

When evaluating Claude Cowork, enterprise security teams asked, "Why can't our EDR see inside?" The answer was that the same isolation keeping Claude contained also kept host-based endpoint detection and response out. From the EDR's perspective, Claude Cowork is an opaque hypervisor process. It can't inspect the guest.

Isolation reduces visibility, and opacity is problematic for teams whose compliance posture depends on endpoint visibility. Our current mitigation is to use pull-based OTLP exports that let administrators retrieve event logs after the fact, but this is not the same as live monitoring.

Design for containment at the environment layer first, then steer behavior at the model layer. Match isolation strength to the user's capacity for oversight. Be wary of custom components. Ultimately, while agents may be a new category of software, their system-level interactions are not.
