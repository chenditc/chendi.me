动态工作流：
让 Claude 自己写调度器

Claude Code 现在可以动态编写并编排自己的多 agent 调度器（harness）。默认的 Claude Code 调度器虽然对编程任务已经很有效，但在长时间运行、大规模并行、高度结构化或对抗性任务上会遇到瓶颈——因为它需要在同一个上下文窗口中同时完成规划和执行。动态工作流解决了这个问题：它执行一个 JavaScript 文件，其中包含特殊函数来生成和协调子 agent，Claude 可以决定每个 agent 使用哪个模型、是否在独立的 worktree 中运行。这意味着 Claude 不再受限于单一上下文窗口，而是能根据任务特点定制一套完整的编排方案——从安全审计、代码迁移到商业计划分析，都可以用一句自然语言触发。比如「用工作流去查 Slack 过去六个月的 #incidents，找出没人提 ticket 的重复根因」，或者「这个测试每 50 次跑挂一次，建一个工作流复现它，搞出互相竞争的假说，找到证据才停」。

Last week, we released dynamic workflows in Claude Code. Claude can now write its own harness on the fly, custom-built for the task at hand.

While the default Claude Code harness is built for coding, it is also useful for many other types of tasks because, as it turns out, many tasks resemble coding tasks. But there are certain classes of tasks where we have had to build custom harnesses on top of Claude Code to achieve peak performance such as Research, security analysis, agent teams, or Code Review.

Workflows allow you to dynamically create harnesses built on top of Claude Code that enable Claude to solve all of those problems more natively. You can also share and reuse these workflows with others.

Dynamic workflows execute a javascript file with a few special functions that help spawn and coordinate subagents. It's particularly useful to know that dynamic workflows can decide which models an agent uses and whether subagents are run in their own worktree, allowing Claude to choose the intelligence level and isolation needed.

三种失败模式：
为什么需要编排

当 Claude 在单一上下文窗口中处理复杂任务时，工作越久越容易掉进三个陷阱。第一个是agent 惰性（agentic laziness）：Claude 在完成了安全审查的 35 项后宣布「任务完成」，但实际上还有 15 项没做——它在部分进度后过早停下。第二个是自我偏好（self-preferential bias）：当你让 Claude 对照评分标准验证自己的结果时，它倾向于给自己打高分，因为人都爱自己写的东西。第三个是目标漂移（goal drift）：经过多轮对话和上下文压缩后，原始目标中的细节——比如「不要做 X」这类约束——会在摘要中丢失，Claude 逐渐偏离最初的方向。动态工作流通过为每个子任务分配独立的 agent 和上下文窗口来结构性地消除这三个问题：每个 agent 只关注一个聚焦的目标，互不干扰。与之前的静态工作流（使用 Claude Agent SDK 或 claude -p 手动编排）相比，Claude Opus 4.8 现在足够聪明，可以为你的具体用例量身定制调度方案，而不是使用通用模板。

Original

When you ask the default Claude Code harness to do a task, it needs to both plan and execute in the same context window. For many coding tasks, this is highly effective, but it can break down over long-running, massively parallel, highly structured and/or adversarial tasks.

This is because the longer Claude works on a complex task in a single context window, the more it becomes susceptible to a few specific failure modes:

Agentic laziness refers to when Claude stops before finishing a particularly complex, multi-part task and declares the job done after partial progress, for example addressing 35 of the 50 items in a security review.

Self-preferential bias refers to Claude's tendency to prefer its own results or findings, especially when asked to verify or judge them against a rubric.

Goal drift refers to the gradual loss of fidelity to the original objective across many turns, especially after compaction. Each summarization step is lossy, and details like edge-case requirements or "don't do X" constraints can get lost.

Creating a workflow helps combat these by orchestrating separate Claude subagents with their own context windows and focused, isolated goals.

You may have previously created a static workflow using the Claude Agent SDK or claude -p to coordinate multiple instances of Claude Code together. But because static workflows need to work for all edge cases, they are usually more generic. With Claude Opus 4.8 and dynamic workflows, Claude is now intelligent enough to write a custom harness tailor-made for your use case.

六大编排模式：
工作流的积木块

动态工作流不是从零开始设计的——Claude 会组合几种经过验证的编排模式来构建工作流。分类路由（classify-and-act）先用分类器判断任务类型，再分配给不同的 agent 处理。扇出合并（fan-out-and-synthesize）将一个大任务拆成多个小步骤并行执行，然后在「屏障」处等待所有结果返回并合并——特别适合每个步骤需要干净上下文以避免交叉污染的场景。对抗验证（adversarial verification）为每个执行 agent 配一个独立的验证 agent，用评分标准对抗性地审查输出。生成过滤（generate-and-filter）先大量生成想法，再用标准过滤去重，只保留通过验证的高质量结果。锦标赛（tournament）让 N 个 agent 用不同方法竞争同一任务，通过配对比较选出赢家——比绝对评分更可靠。循环直到完成（loop until done）则持续生成 agent 直到满足停止条件，而不是固定次数。

Original

There are a few common patterns that Claude might use and compose together when building workflows:

Classify-and-act: Use a classifier agent to decide on the type of task, and then route to different agents or behavior based on the task. Or, use a classifier at the end to determine output.

Fan-out-and-synthesize: Split up a task into many smaller steps, run an agent on each step and then synthesize those results. This is particularly useful for when there are a large number of smaller steps, or when each step benefits from its own clean context window so they don't interfere or cross-contaminate. The synthesize step is a barrier—it waits for all the fan-out agents, then merges their structured outputs into one result.

Adversarial verification: For each spawned agent, run a separate spawned agent to adversarially verify its output against a rubric or criteria.

Generate-and-filter: Generate a number of ideas on a topic and then filter them by a rubric or by verification, dedupe duplicates and return only the highest quality, tested ideas.

Tournament: Instead of dividing the work, have agents compete on it. Spawn N agents that each attempt the same task using different approaches. Prompts or models then judge the results in a pairwise fashion using a judging agent until you have a winner.

Loop until done: For tasks with an unknown amount of work, loop spawning agents until a stop condition is met (no new findings, or no more errors in the logs) instead of a fixed number of passes.

Think creatively of when and how to ask Claude Code to make dynamic workflows. I've found that workflows are sometimes even more useful for non-technical work.

Migrations and refactors: Bun was rewritten from Zig to Rust using workflows. The key is to break down the task into a series of steps that need to be operated on for example callsites, failing tests, modules, etc. Spin off a subagent for every fix in a worktree to make the fix, then have another agent adversarially review, and merge them.

Deep research: We published a deep research skill (/deep-research) inside Claude Code that uses dynamic workflows. Specifically, it fans-out web searches, fetches sources, adversarially verifies their claims, and synthesizes a cited report.

Deep verification: On the other hand, if you have a report where you want to check and source every factual claim that it references you may want to generate a workflow which has one agent identify all of the factual claims and then spin off a subagent to check each one in-detail.

Sorting: You may have a list of items that you want to sort by some qualitative measurement that you believe that Claude Code is good at evaluating. But if you try to sort 1000+ rows in one prompt, quality degrades and it won't fit in context. Instead run a tournament, a pipeline of pairwise-comparison agents.

Root-cause investigation: Debugging works best when you come up with several independent hypotheses and test them. A workflow can structurally prevent self-preferential bias by spinning up agents to generate hypotheses from disjoint evidence.

Triaging at scale: A triage workflow classifies each item, dedupes against what's already tracked, and takes action. A useful pattern for triage workflows is quarantine—barring agents that read untrusted public content from taking high-privilege actions.

Workflows are new. While there are many use cases where it will create outsized results, they are not needed for every task and may end up using significantly more tokens.

It's best to use workflows creatively to push Claude Code in ways that you haven't previously. For regular coding tasks, try and ask yourself: does it really need more compute? For example, most traditional coding tasks do not need a panel of 5 reviewers.

Detailed prompting, using the specific techniques we described above, for dynamic workflows creates the best results.

Workflows are not just for large tasks. You can prompt the model to use a "quick workflow." For example, you can create a quick adversarial review of an assumption.

When using workflows that can be repeated, for example triage, research, or verification, pair them with /loop to be run at regular intervals, and /goal to set a hard completion requirement.

You can set explicit token usage budgets for dynamic workflows to limit how many tokens a task uses. You can prompt it with a budget like: "use 10k tokens," which will set the cap.

You can save workflows by pressing "s" in the workflow menu. You can check these into ~/.claude/workflows or distribute them via a skill.

To share them via a skill, put your JavaScript workflow files in the skill and folder and reference them in the SKILL.MD. To allow for more flexibility, you may want to prompt Claude to think of the workflows in the skill as a template instead of a script that needs to be run verbatim.

Workflows are a helpful new way to extend Claude Code. I encourage you to think of them as a starting point to explore new ways to use Claude to help accomplish your tasks. There is still much to discover in how to use them best.

六大编排模式详解

分类路由（classify-and-act）是最基础的模式：先用一个分类器 agent 判断任务类型——是 bug 修复、功能实现还是代码审查——然后根据分类结果路由到不同的执行 agent 或行为分支。分类器也可以放在末端用来判断输出质量。扇出合并（fan-out-and-synthesize）把一个大任务拆成多个小步骤，每个步骤由独立的 agent 在干净的上下文窗口中并行执行——这样可以避免步骤之间的交叉污染。合并步骤是一个「屏障」：它等待所有扇出 agent 完成，然后将它们的结构化输出合并为一个结果。对抗验证（adversarial verification）是质量保障的核心：为每个生产 agent 配备一个独立的验证 agent，用评分标准或准则对其输出进行对抗性审查——因为同一个 agent 验证自己的结果会受自我偏好影响。生成过滤（generate-and-filter）先让 agent 大量生成想法，然后用标准过滤、验证、去重，只返回最高质量的、经过测试的结果。锦标赛（tournament）让 N 个 agent 用不同方法竞争同一任务，然后通过裁判 agent 做配对比较来选出赢家——因为比较判断（comparative judgment）比绝对评分更可靠。循环直到完成（loop until done）适合工作量未知的任务：持续生成 agent 直到满足停止条件——比如「没有新发现」或「日志中不再有错误」——而不是固定跑 N 轮。

Classify-and-act: Use a classifier agent to decide on the type of task, and then route to different agents or behavior based on the task. Or, use a classifier at the end to determine output.

Fan-out-and-synthesize: Split up a task into many smaller steps, run an agent on each step and then synthesize those results. This is particularly useful for when there are a large number of smaller steps, or when each step benefits from its own clean context window so they don't interfere or cross-contaminate. The synthesize step is a barrier—it waits for all the fan-out agents, then merges their structured outputs into one result.

Adversarial verification: For each spawned agent, run a separate spawned agent to adversarially verify its output against a rubric or criteria.

Generate-and-filter: Generate a number of ideas on a topic and then filter them by a rubric or by verification, dedupe duplicates and return only the highest quality, tested ideas.

从迁移到模型路由

迁移和重构——Bun 从 Zig 重写为 Rust 就用了工作流：把任务拆成调用点、失败测试、模块等步骤，每个修复在独立 worktree 中进行，再由对抗审查 agent 审查后合并；建议限制资源密集型命令以最大化并行度。深度研究——Claude Code 的 /deep-research 技能使用动态工作流：扇出搜索、获取源、对抗验证事实、合成带引用的报告；也可以用来从 Slack 编译状态报告或深入探索代码库。深度验证——让一个 agent 识别报告中所有事实声明，再为每个声明分配子 agent 逐一核查，还可以加一个验证 agent 检查来源质量。排序——1000+ 行用单一提示排序会降质且超出上下文限制，所以用锦标赛模式做配对比较，每次比较是独立 agent，确定性循环管理对阵表。规则遵循——为 CLAUDE.md 中难以遵守的规则各配一个验证 agent，再用怀疑者 agent 审查规则本身以减少误报；反过来也能用：挖掘历史会话中的重复纠正，聚类后蒸馏回 CLAUDE.md。根因调查——分别从日志、文件、数据生成假说，交给验证和反驳 panel 审查，不仅限于代码——销售下滑和管道故障也适用。大规模分流——分类、去重、行动三步走，关键模式是「隔离」：读取不可信公共内容的 agent 不得执行高权限操作，配合 /loop 持续运行。探索与品味——用评分标准让审查 agent 判断方案是否达标，或通过锦标赛排名。轻量 Eval——在 worktree 中分出 agent 执行，再由比较 agent 对照标准评分。模型路由——分类器 agent 先分析任务复杂度（比如 auth 模块有多少文件），再决定路由到 Sonnet 还是 Opus。

Original

Migrations and refactors: Bun was rewritten from Zig to Rust using workflows. The key is to break down the task into a series of steps that need to be operated on for example callsites, failing tests, modules, etc. Spin off a subagent for every fix in a worktree to make the fix, then have another agent adversarially review, and merge them. Consider telling the agent not to use resource intensive commands so that you can maximally parallelize without running out of resources on your machine.

Deep research: We published a deep research skill (/deep-research) inside Claude Code that uses dynamic workflows. Specifically, it fans-out web searches, fetches sources, adversarially verifies their claims, and synthesizes a cited report. But you may do this sort of research for more than just web searches.

Deep verification: If you have a report where you want to check and source every factual claim that it references you may want to generate a workflow which has one agent identify all of the factual claims and then spin off a subagent to check each one in-detail. You could also have a verification agent check the source subagent to make sure its source is high quality.

Sorting: You may have a list of items that you want to sort by some qualitative measurement. But if you try to sort 1000+ rows in one prompt, quality degrades and it won't fit in context. Instead run a tournament, a pipeline of pairwise-comparison agents (comparative judgment is more reliable than absolute scoring).

Memory and rule adherence: If you have a particular set of rules that you find Claude misses or struggles with, create a workflow with a list of rules that must be checked by verifier agents—one verifier per rule. The reverse direction works too: mine your recent sessions and code review comments for corrections you keep making, cluster them with parallel agents, adversarially verify each candidate, and distill the survivors back into a CLAUDE.md.

Root-cause investigation: A workflow can structurally prevent self-preferential bias by spinning up agents to generate hypotheses from disjoint evidence. Each hypothesis can then face a panel of verifiers and refuters. This isn't just for code—workflows can be used for sales, data engineering, or any post-mortem exercise.

Triaging at scale: A triage workflow classifies each item, dedupes against what's already tracked, and takes action. A useful pattern for triage workflows is quarantine—barring agents that read untrusted public content from taking high-privilege actions. Pair triage workflows with /loop to have Claude do this continuously.

Exploration and taste: Workflows can be useful when exploring different approaches to a solution, especially when it is taste based. Try asking Claude to explore a bunch of solutions, and give a review agent a rubric for what a good solution looks like.

Evals: You can run lightweight evals by spinning off separate agents in a worktree and then spinning off comparison agents to compare and grade the specific outputs against a rubric.

Model and intelligence routing: Create a classifier agent tuned to your tasks that decides which model to use. A classifier agent can do research and then route to Sonnet or Opus based on the expected complexity of the task.
