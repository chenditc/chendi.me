ALGORITHM

找到和你品味相同的人，看他们还点赞了什么

For You Feed 的核心算法简单得令人意外：它找到那些和你点赞过相同帖子的人，然后看看他们最近还点赞了什么——就是这样。这本质上是一种协同过滤算法，不需要用户画像、不需要内容分析、不需要机器学习模型。因为用户的点赞行为本身就是最可靠的品味信号，所以 spacecowboy 把整个推荐系统建立在这一个简洁的假设之上。

ARCHITECTURE

一个 Go 进程搞定一切——消费、存储、推荐、托管

整个系统就是一个 Go binary，它同时负责四件事：消费 Bluesky 的 Jetstream firehose（实时数据流）、把数据存到 SQLite、响应推荐请求、托管 playground 网站。没有微服务拆分，没有消息队列，没有外部缓存——因为所有东西都在同一个进程里，进程内缓存就能替代 Redis，省去了进程间通信和序列化的全部开销。

SCALING

25 QPS 只用 37% CPU——降级模式可服务全部 Bluesky 用户

72000 日活用户，每人平均 22 次请求，日常流量在 15-25 QPS 之间。在 25 QPS 时 CPU 使用率只有 37%，也就是说现有硬件还能轻松承受 3 倍用户量。更厉害的是，当负载变高时系统会自动切换到更便宜的算法参数——计算量减少超过 10 倍，但推荐质量几乎没有下降。在降级模式下只用 24 核中的 7 核，理论上可以支持 210 万用户。而 Bluesky 全部日活也只有约 100 万——也就是说这一台客厅游戏电脑，理论上能服务整个平台。

NETWORK

Tailscale + $7 VPS——不暴露家庭 IP 的代理架构

家里的服务器不直接暴露在公网上。一台每月 $7 的 OVH VPS 充当代理：nginx 接收推荐请求，转发给一个 Go 写的 dispatch 进程。Dispatch 先验证 JWT token（通过 DID 文档查询，这样可以避免暴露家庭 IP），然后通过 Tailscale 把请求路由到客厅的游戏电脑——在 Tailscale 网络里它的地址就是 http://gaming:8090。维护期间 dispatch 可以返回预设帖子列表，保证用户不会看到空白 feed。

SQLITE

SQLite 419GB——整数 ID 映射 + mutex 写 + 90 天保留

所有数据都存在 SQLite 里，spacecowboy 选择它的一个关键理由是可测试性——单元测试可以直接在内存中创建数据库，不需要 mock 存储层。数据库设计很精巧：每个帖子的 AT URI 被映射成整数 ID 以节省内存，用户同样如此。读取用 5 个并发连接，写入用 Go mutex 保证单线程——避免了 db.SetMaxOpenConns(1) 这种把读也序列化的常见做法。数据只保留 90 天，一个 cleanup goroutine 每 24 小时清理过期数据。VACUUM 操作不跑，因为要花好几个小时。

Database

All data lives in SQLite. A key advantage is testability—databases can be created in-memory for unit tests without mocking the storage layer. Each post AT URI receives an integer identifier. The database uses five concurrent read connections. A Go mutex enforces single-threaded write access. Data retention spans 90 days. The SQLite file measures 419GB; vacuum operations aren't run due to performance costs.

IN-PROCESS CACHE

进程内 LRU 缓存——99% 从内存读取，50GB 常驻

推荐系统最重要的性能秘密是进程内缓存（hashicorp/golang-lru）。因为读写都在同一个进程里，所以不需要 Redis 这样的外部缓存——没有进程间通信开销，没有序列化开销。几乎 100% 的推荐数据都从缓存中读取，而不是从磁盘。进程吃掉了大约 50GB 内存，其中 99% 是缓存。这个架构的代价是进程重启后会出现剧烈的性能下降，直到缓存重新预热——但 spacecowboy 认为这是值得的 tradeoff。

Cache

For You relies heavily on in-process caches (hashicorp/golang-lru). Because writers and readers operate in a single process, separate services like Redis aren't needed. In-process caching avoids interprocess communication and serialization overhead, with nearly 100% of recommendation data sourced from cache rather than disk. The tradeoff: process restarts cause dramatic slowdowns until caches warm up.

A/B TESTING

Parquet + DuckDB——一个人的数据分析流水线

spacecowboy 不只是在跑算法——他还在认真做数据分析。一个独立的 200GB SQLite 数据库记录了每次返回给用户的帖子，当用户点击「show more」或「show less」时这些信号通过 firehose 回传并记录。数据定期导出为每日一个的 parquet 文件（平均 2.6GB），然后用 DuckDB 做查询。他跑了一个月的 A/B 测试，结果显示新算法让用户点击「show less」的概率降低了 2.6%，「show more」增加了 5.7%。
