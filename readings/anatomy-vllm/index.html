vLLM 解剖：
一个高吞吐推理系统的全部内脏

这篇 41 分钟的深度解析从最基础的 LLM Engine 开始，逐层构建出一个完整的在线、异步、多GPU、多节点推理系统。LLM Engine 是 vLLM 的基本构建单元——它本身就已经支持高吞吐离线推理，但还不能对外提供 API 服务。Engine 内部由三个核心组件构成：调度器（决定哪些请求参与当前 step）、KV Cache 管理器（维护一个包含数十万个可用 block 的 free_block_queue，在 paged attention 中按需分配和回收）、以及模型执行器（负责实际的前向传播计算）。从这个基础出发，文章依次叠加了调度策略、prefix caching、speculative decoding、tensor parallelism、data parallelism，最终抵达一个能用一条 curl 命令调用的完整分布式推理服务。

Original

The LLM engine is the fundamental building block of vLLM. On its own, it already enables high-throughput inference - but only in an offline setting. You can't serve it to customers over the web yet.

Engine core itself is made up of several sub components: The KV-cache manager maintains a free_block_queue - a pool of available KV-cache blocks (often on the order of hundreds of thousands, depending on VRAM size and block size).

请求的一生：
从 prompt 到 token

每个请求在 vLLM 中经历一段完整的旅程。首先是输入验证与注入：对每个 prompt 进行 tokenize、创建请求对象并分配唯一 ID，然后喂入引擎。接下来引擎进入主循环——只要还有待处理的请求，就反复调用 step() 函数。每个 step 包含三个阶段：第一步调度器决定哪些请求参与这一步（包括 prefill 和 decode 请求的混合），第二步将调度结果送入模型执行器执行前向传播，第三步处理输出——检查停止条件、更新采样状态、收集已完成的请求。因为前向传播会把整个 batch 展平成单一序列，由定制 kernel 高效处理，所以连续批处理（continuous batching）从架构层面被自然支持——即使在同步引擎中也是如此。

Original

The first step is to validate and feed requests into the engine. For each prompt we: tokenize, create request objects and assign unique IDs, then feed into the engine.

Next, as long as there are requests to process, the engine repeatedly calls its step() function. Each step has three stages: schedule, execute forward pass, process output.

Because the forward pass flattens the batch into a single sequence and custom kernels handle it efficiently, continuous batching is fundamentally supported even in the synchronous engine.

调度器的博弈：
Prefill vs Decode

推理引擎处理两种截然不同的工作负载。Prefill 是处理新到的完整 prompt——计算密集型，一次性处理所有输入 token 并填充 KV cache。Decode 是逐个生成输出 token——内存带宽受限，每步只处理一个新 token 但需要读取已有的完整 KV cache。V1 调度器的关键创新是能在同一个 step 中混合两种请求（V0 只能二选一）。调度优先级是 decode 优先：先处理正在运行队列中的 decode 请求，为每个请求分配新的 KV cache block 和采样参数；然后处理等待队列中的 prefill 请求，根据剩余 token 预算决定能接纳多少新请求。allocate_slots 函数负责在 KV cache 管理器中实际分配 block——如果新 token 跨越了 block 边界就追加新 block，否则复用当前 block 的剩余空间。

Prefix Caching 和 Speculative Decoding 的内部机制是什么？

四大进阶能力：
在核心循环上叠加

在基础引擎之上，vLLM 叠加了四种关键的高级特性，每种都正交于主流程。Chunked Prefill 把超长 prompt 切成固定大小的 chunk，防止单个长请求垄断一整个 step——实现很简洁：限制每步新 token 数上限，底层索引逻辑自动处理。Prefix Caching 对 KV cache block 计算哈希值，相同前缀的请求可以直接复用已有的 KV block，避免重复计算。Guided Decoding 在每个解码步用基于语法的有限状态机约束 logits，确保输出符合指定的正则或上下文无关文法——一个 bitmask 编码哪些 token 被允许。Speculative Decoding 用小模型快速提议 k 个 token，然后用大模型一次性验证——数学上证明等价于从大模型直接采样。

Chunked prefill is a technique for handling long prompts by splitting their prefill step into smaller chunks. Without it, we could end up with a single very long request monopolizing one engine step.

Guided decoding is a technique where, at each decoding step, the logits are constrained by a grammar-based finite state machine.

Speculative decoding speeds this up by introducing a smaller draft LM. The draft proposes k tokens cheaply. The accept/reject rule guarantees that in expectation the sequence is distributed exactly as if we had sampled token by token from the full model.

从单 GPU 到集群：
三层扩展架构

当模型权重超出单 GPU 显存时，vLLM 提供三层递进的扩展方案。第一层是张量并行（TP）：将模型分片到同一节点的多个 GPU 上（如 TP=8）。如果还不够，第二层是流水线并行（PP）：跨节点的不同 GPU 处理模型的不同层。这两层通过 MultiProcExecutor 协调——从引擎视角看，所有多进程复杂度都被 execute_model 调用抽象掉了。第三层是数据并行（DP）：复制整个模型到多个副本，加上轻量级的 DP 协调层和负载均衡。最终，一个 FastAPI 服务器挂载 OpenAI 兼容的 /completion 和 /chat/completion 端点，整个分布式架构被封装在一条 curl 命令的背后。

多节点部署和请求全生命周期的完整架构是什么样？

延迟 vs 吞吐：
不可兼得的 roofline

在系统层面，两个指标永远在博弈。延迟对交互式应用至关重要——用户在等待回复。吞吐对离线工作负载更重要——合成数据生成、数据清洗、批量推理。它们的矛盾来自 batch size：batch size 减小时，每步延迟降低（ITL 更短，单个 token 不用和其他请求竞争）；batch size 增大时，GPU 利用率更高，吞吐飙升。Roofline 模型解释了这背后的物理限制：在饱和 batch size B_sat 之下，步延迟由 HBM 带宽主导（逐层搬运权重到片上内存），步时间几乎不变；超过 B_sat 后，计算成为瓶颈，步时间线性增长。vLLM 提供了 auto-tune 脚本，在给定 SLO 约束下（如 p99 端到端延迟 < 500ms）自动搜索最优配置参数。

At the highest level there are two competing metrics: latency and throughput. Latency matters most for interactive applications. Throughput matters in offline workloads.

The tradeoff becomes clear when looking at how batch size B affects a single decode step. As B decreases toward 1, ITL drops. As B increases toward B_sat, throughput improves.

A roofline model helps: below B_sat, step time is dominated by HBM bandwidth (streaming weights layer-by-layer), so step latency is nearly constant regardless of B.

Prefix Caching：
哈希一次，复用无数次

Prefix Caching 的核心思想是：如果两个请求有相同的前缀，第二个请求不需要重新计算前缀的 KV cache。实现分三步走。第一步哈希：在调度阶段，对请求 token 按 block 大小（默认 16）分块，每块计算一个 BlockHash（包含 token 内容、可选的多模态哈希、LoRA ID、cache salt）。第二步查找：用 find_longest_cache_hit 在 cached_block_hash_to_block 映射中线性搜索匹配——首次请求无命中。第三步缓存：allocate_slots 中调用 coordinator.cache_blocks，将新分配的 KV block 与其哈希关联起来存入映射表。前向传播后这些 block 就填满了实际的 KV 值。当第二个相同前缀的请求到来时，find_longest_cache_hit 找到所有 n 个 block 的匹配，直接复用——只需计算新增的 token。KV block 只有在被从 free_block_queue 中弹出重新分配时才会失效。

During the first generate call, in the scheduling stage, the engine invokes hash_request_tokens. The list is stored in self.req_to_block_hashes[request_id].

Next, the engine calls find_longest_cache_hit to check if any of these hashes already exist in cached_block_hash_to_block. On the first request, no hits are found.

On a second generate call with the same prefix, find_longest_cache_hit finds matches for all n blocks. The engine can reuse those KV blocks directly.

KV-cache blocks become invalid only when they're about to be reallocated from the free_block_queue.

Speculative Decoding：
小模型提议，大模型验证

自回归生成的瓶颈在于每生成一个 token 都需要一次完整的前向传播——每步都要重新加载和应用所有模型权重，只为计算一个 token。Speculative Decoding 的解法是引入一个小型 draft 模型：它快速提议 k 个候选 token，然后大模型一次前向传播同时验证所有 k 个。接受/拒绝规则保证了最终序列的分布在数学期望上与直接从大模型逐 token 采样完全等价。vLLM V1 实现了三种不依赖独立 draft 模型的方案：N-gram 在已有上下文中查找匹配的 n-gram 作为提议（零额外计算）；EAGLE 对大模型做手术——保留 embedding 和 LM head，用轻量 MLP 替换 transformer stack 作为 draft；Medusa 在大模型的 embedding 层顶部训练辅助线性 head，并行预测后续 k 个 token。

In autoregressive generation, each new token requires a forward pass of the large LM. This is expensive — every step reloads and applies all model weights just to compute a single token!

Speculative decoding speeds this up by introducing a smaller draft LM. The draft proposes k tokens cheaply. The accept/reject rule guarantees that in expectation the sequence is distributed exactly as if we had sampled token by token from the full model.

vLLM V1 implements n-gram, EAGLE, and Medusa proposal schemes.

多 GPU 编排：
MultiProcExecutor

当需要 TP > 1 或 PP > 1 时，vLLM 启用 MultiProcExecutor 来协调多个 GPU worker。每个 worker 进程独立执行三个关键步骤：load_model（加载分片后的模型权重）、determine_available_memory（通过 profile 确定可用 KV cache 内存）、initialize_cache（按 block 大小分配 KV cache 内存池）。关键的设计抽象是：从 engine 的视角，MultiProcExecutor 和单进程的 UniprocExecutor 有完全相同的接口——都是调用 execute_model。所有多进程通信、模型分片、梯度同步的复杂度都被封装在 executor 内部。这意味着上层的调度逻辑、prefix caching、speculative decoding 等特性完全不需要知道底层跑了几个 GPU，实现了真正的关注点分离。

Suppose your model weights no longer fit into a single GPU's VRAM. The first option is to shard the model across multiple GPUs on the same node using tensor parallelism (e.g., TP=8).

From the engine's perspective, nothing has changed — all of this multiprocessing complexity is abstracted away through a call to model executor's execute_model.

请求全生命周期：
curl 到 token 的完整路径

在完整的分布式部署中，一条 curl 请求经历的完整路径是这样的。请求首先到达 FastAPI 服务器（挂载了 OpenAI 兼容端点 /v1/completions），被路由到 AsyncLLM（异步引擎包装器）。AsyncLLM 内部创建了 DPLBAsyncMPClient（数据并行、负载均衡、异步、多进程客户端），它通过 DP 协调器与各引擎核心通信。DP 协调器是前端和后端之间的中介——它感知每个副本的缓存状态以做 cache-aware 路由、在 DP 副本之间同步 scheduling 状态以保证 lockstep 执行、并向前端报告引擎统计信息。每个 DP 副本内部，EngineCoreProc 运行主线程（scheduler + executor）、输入线程（接收新请求）和输出线程（发送结果），最终 token 通过 SSE（Server-Sent Events）流式返回给用户。

We instantiate an AsyncLLM object (an asyncio wrapper around the LLM engine). Internally this creates a DPLBAsyncMPClient (data-parallel, load-balancing, asynchronous, multiprocessing client).

The DP coordinator mediates between the frontend (API server) and backend (engine cores). It: provides cache-aware routing, synchronizes scheduling state, and reports engine statistics.

Finally, the main server process creates a FastAPI app and mounts endpoints such as OpenAIServingCompletion and OpenAIServingChat.
