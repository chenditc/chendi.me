当我们让 AI Agent 去订机票、查日历、发邮件——它真的能搞定吗？

当我们说「测试 AI Agent」的时候，我们到底在测什么？现有的 benchmark 让 Agent 做的事情是这样的：给一个固定的问题，等一个固定的答案，整个世界在 Agent 思考的时候是静止的。但真实世界不是这样运作的——你让 AI 帮你订下周的会议室，它查日历的时候别人可能已经把那个时段占了；你让它帮你回邮件，新邮件可能在它处理的过程中不断涌入。因此 Meta 的研究团队提出了 Gaia2——一个在动态、异步环境中测试 AI Agent 的 benchmark，包含 1120 个场景和 7 个能力维度。

Abstract

We introduce Gaia2, a benchmark for evaluating LLM agents in dynamic, asynchronous environments. Built on ARE (Agents Research Environments), a novel event-driven platform, Gaia2 features 1,120 scenarios spanning 7 capability splits—Execution, Search, Ambiguity, Adaptability, Time, Noise, and Agent-to-Agent—within a realistic Mobile environment of 12 apps and 101 tools.

ACT I · 问题

静态考场测不出真本事

过去几年涌现了很多 Agent benchmark：GAIA 让 Agent 回答需要多步推理的问题，AgentBench 让 Agent 在网页和代码环境中完成任务，SWE-bench 让 Agent 修复 GitHub issue。但这些 benchmark 有一个共同的假设——环境是静态的。Agent 看到的状态在它操作的过程中不会改变，没有新消息会弹出来打断它，也不需要跟别的 Agent 协调。这就像让学生在完全安静的教室里考试——但现实世界的「考场」是嘈杂的、变化的、多人同时在场的。Gaia2 打破了这个静态假设：在它的测试环境中，事件会按时间触发，通知会异步到达，其他 Agent 可能同时在修改共享状态。

Introduction

Existing agent benchmarks such as GAIA, AgentBench, and SWE-Bench evaluate agents in static environments where the world state does not change during execution. However, real-world tasks require agents to handle dynamic state changes, asynchronous notifications, and multi-agent coordination. Gaia2 addresses this gap by introducing an event-driven simulation platform where the environment evolves over time.

ACT II · 平台

ARE：一切皆事件

Gaia2 的底座是一个叫 ARE（Agents Research Environments）的模拟平台。它的核心思想可以用一句话概括——「一切皆事件」。整个模拟世界由五个概念构成：App（工具集合）、Environment（全局状态）、Event（定时或条件触发的状态变更）、Notification（给 Agent 的异步通知）、Scenario（一次完整的测试场景）。这五个概念组合起来，就能模拟从简单的「查个联系人」到复杂的「两个 Agent 协作完成跨应用任务」的所有场景。

Section 3: ARE

ARE introduces five core primitives: Apps bundle related tools, Environments maintain global state, Events trigger state changes on schedules or conditions, Notifications deliver asynchronous messages to agents, and Scenarios define complete test cases with setup, instructions, and verification criteria.

ACT II · 环境

一部虚拟手机：12 App × 101 工具

Gaia2 的第一个具体环境是一部「虚拟手机」—— Mobile 环境。它模拟了 12 个常见的手机 App：通讯录、短信、电话、Gmail、日历、备忘录、提醒事项、文件管理、地图、浏览器、时钟和音乐，共提供 101 个工具函数。更巧妙的是数据生成方式：系统先创建一个「宇宙」——包含虚拟用户的社交关系、工作背景、兴趣爱好，然后基于这些人设自动生成逼真的短信记录、邮件往来、日历安排等数据，因此所有 App 中的数据是内在一致的。

ACT III · 测什么

七把标尺，七个维度

Gaia2 把 Agent 的能力拆成了七个维度来考察，就像高考分科一样——Execution（能不能正确调用工具）、Search（能不能跨应用找信息）、Ambiguity（能不能处理模糊指令）、Adaptability（条件变了能不能调整策略）、Time（能不能正确处理时间敏感的任务）、Noise（能不能过滤无关通知的干扰）、Agent2Agent（两个 Agent 能不能协作）。这七个维度不是随意选的，而是对应了真实世界中 Agent 会遇到的七类典型挑战。1120 个场景按这七个维度分组，每个维度 100-200 个场景。

ACT IV · 结果

成绩单揭晓：最强的也只搞定了 42%

论文测试了 11 个模型，结果颇有意思。GPT-5（高算力版）以 42% 的 pass@1 领跑，但这个分数本身就说明 Gaia2 有多难——最强的模型也只能搞定不到一半的场景。Claude-4-Sonnet 紧随其后拿到 35%，Gemini-2.5-Pro 拿到 28%。开源模型中 Kimi-K2 以 21% 领先。最关键的发现是：没有任何一个模型在所有七个维度上都是最强的。GPT-5 在 Execution 和 Search 上碾压其他模型，但在 Time 维度上却不是第一名。

ACT IV · 洞察

越强的模型，越容易被时间绊倒

论文中最有意思的发现来自 Time 维度：更强的模型反而表现更差。这听起来反直觉，但原因很合理——能力更强的模型倾向于「想太多」，在时间敏感的任务中花太多步骤去完善答案，反而错过了时间窗口。另一个发现是关于 Agent2Agent 协作的：协作对弱模型的帮助远大于强模型。GPT-5 从单 Agent 的 34% 只提升到 37%，但 Llama-4-Maverick 从 11% 跳到 16%——弱模型更能从「队友」身上获益，因为它们可以把自己不擅长的子任务分给搭档。

ACT V · 可信度

裁判也要考核：0.98 的人机一致率

一个 benchmark 的可信度取决于它的判题系统。Gaia2 的 ARE Verifier 采用了一个巧妙的设计：把 Agent 可以调用的工具分成「读工具」（查询状态）和「写工具」（修改状态）。验证时，Verifier 只需要检查环境的最终状态——Agent 是否通过写工具产生了正确的副作用。这种基于副作用的验证方式避免了判断 Agent「思考过程」的模糊性，达到了 0.98 的人机一致率和 0.99 的精确率。这意味着 ARE Verifier 的判断几乎和人类专家一样可靠。

Section 5: Verification

The ARE Verifier separates agent tools into "read" tools (state queries) and "write" tools (state modifications). Verification checks only the final environment state—whether the agent produced the correct side effects through write tools. This approach achieves 0.98 agreement and 0.99 precision compared to human expert labels.

ARE 架构 · 事件系统

Events：让世界「活」起来的心跳

ARE 中的 Events 有三种触发方式：Scheduled（在指定时间触发，比如「上午 9 点发送一封邮件」）、Conditional（满足特定条件时触发，比如「当 Agent 读取了某条消息后，对方开始打字回复」）、以及 Probability（以一定概率触发，模拟真实世界的随机性）。每个 Event 执行时可以修改 Environment 的状态，也可以触发新的 Notification 通知 Agent。EventLoop 按照时间轴严格调度所有 Events，确保因果关系正确——先发生的事件一定先被处理，后续事件看到的是更新后的状态。

Events in ARE can be triggered in three ways: scheduled (at a specific time), conditional (when a condition is met, such as the agent reading a message), and probability-based (with a given likelihood at each tick). The EventLoop processes events in chronological order, ensuring causal consistency. Each event can modify environment state and generate notifications.

ARE 架构 · 异步通信

Notification：打断你的「推送通知」

Agent 不是在真空中工作的。当环境状态发生变化时——比如收到新短信、日历事件临近、有人给你打电话——ARE 会通过 Notification 系统通知 Agent。这模拟了真实手机上推送通知的机制。关键在于，Notification 是异步到达的：Agent 正在处理任务 A 的时候，可能突然收到与任务 B 相关的通知。Agent 必须决定这条通知是否重要、是否需要中断当前工作去处理它。这正是 Noise 维度测试的核心能力——在信息洪流中保持专注，同时不遗漏真正重要的信号。

虚拟手机 · App 生态

12 个 App，四大类能力

Mobile 环境的 12 个 App 不是随意选择的，它们覆盖了手机使用的四大类场景：通信类（Messages、Phone、Gmail——用于发送和接收信息）、组织类（Calendar、Notes、Reminders——用于安排和记录）、信息类（Contacts、Files、Maps、Browser——用于查找和获取信息）、以及工具类（Clock、Music——辅助功能）。每个 App 都有明确的「读工具」和「写工具」划分：比如 Gmail 的读工具是 get_emails，写工具是 send_email。这种划分不仅让 Agent 的操作更结构化，也让 Verifier 能精确判断任务是否完成。

虚拟手机 · 数据生成

先造人设，再造数据

如何创造一个逼真的虚拟手机世界？Gaia2 的方法是先定义角色设定（persona）——用户叫什么名字、在哪里上班、有哪些朋友、兴趣爱好是什么。然后用 LLM 基于这些人设生成各 App 的数据：短信记录反映社交关系的亲疏远近，邮件内容与工作背景匹配，日历安排体现生活习惯。这确保了数据之间的内在一致性——同一个联系人在短信、邮件和日历中的信息是连贯的，不会出现「短信里叫小明，邮件里变成 Mike」的穿帮。Scenario 的构建也遵循类似流程：先由人类标注员设计任务框架，再由 LLM 生成具体细节，最后由人类审核验证。

七个维度 · 基础能力

前四把标尺：从执行到应变

Execution 是最基础的维度——给你明确的指令（「给张三发一条短信说明天开会」），你能不能正确调用对应的工具完成任务？Search 把难度提升一档——信息分散在多个 App 中（联系人在通讯录、邮件地址在 Gmail、最近的聊天在 Messages），Agent 需要跨应用检索才能拼出完整答案。Ambiguity 测试的是模糊指令处理能力——「帮我联系那个人」，哪个人？Agent 需要根据上下文推断。Adaptability 最有挑战——任务执行到一半条件变了（会议室被占了、航班取消了），Agent 能不能灵活调整计划而不是傻傻地执行原来的步骤？

七个维度 · 高级能力

后三把标尺：时间、噪声与协作

Time 是最有挑战性的维度——Agent 必须在正确的时间采取行动。比如「在会议开始前 15 分钟发送提醒」，太早或太晚都不算完成。这个维度暴露了一个反直觉的现象：更强的模型反而更容易超时，因为它们花太多步骤去「想清楚」。Noise 模拟了信息过载——大量无关通知涌入（垃圾邮件、社交消息、天气推送），Agent 必须在噪声中识别真正需要处理的信号。Agent2Agent 是最新颖的维度——两个 Agent 必须通过共享的 Notes App 进行隐式协调来完成一个需要双方配合的任务，没有直接通信通道，只能靠在笔记里留言来传递意图。
