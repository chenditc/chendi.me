不是 LLM 不够大，
是缺一个 GPS

从远古的太阳月亮到地图、指南针，再到今天的 GPS 导航，人类的每次探索都依赖一个好的「导引者」。IBM Research 的 Nicholas Fuller 认为，在 agentic AI 时代，AI agent 确实有潜力实现可扩展的企业 AI 采用，但要释放这个潜力，需要一个智能导引——Agent Logic。Agent Logic 是一组运行在 agentic 层的软件原语——知识图谱、算法、程序分析库——它们有意识地将 LLM 引导向企业工作流的方向，同时缩小上下文空间。这么做的结果是：在更高精度的同时，实现更低的 token 消耗和更少的幻觉。核心论点很清晰：单靠 LLM 的大上下文窗口并不能解决企业 AI 落地的问题，你还需要一个 GPS 来告诉 AI 该走哪条路。

Guides have aided humanity throughout history. Prehistoric civilizations understood that the sun and the moon could be used to navigate vast distances on land and the high seas. Over time, various journeys facilitated the production of maps for better planning and faster travel time to repeat destinations. Centuries later, the introduction of the compass enabled seagoers to achieve greater accuracy in seeking unexplored destinations. And today, GPS navigation apps guide our every journey. In today's world of agentic AI, AI agents, admittedly, have the potential to enable scalable AI adoption, transforming industries as we know them. However, an intelligent guide, agentic logic, is needed to realize this potential by fueling high agent quality, cost-effectiveness, and consequent end-user trust.

Agent logic is software primitives, such as knowledge graphs, algorithms, program analysis libraries, which operate at the agentic layer (within an agent harness) and can intentionally steer the LLM in the direction of the enterprise workflow, reducing the context space. In so doing, have strong tendency to drive more performant outcomes in a more cost-effective manner.

企业工作流的三个特征：
为什么 LLM 独木难支

大量研究指出 AI pilot 项目的失败率惊人地高，同时也强调 AI 必须在企业工作流的核心运作才能实现可扩展的采用。而企业工作流有三个关键特征：首先，它们是动态且长时间运行的；其次，它们拥有大量 API、数据库和服务；第三，它们常常受到业务策略和/或法规的约束。要让 agent 在这样的环境中有效运作，自然需要扩大模型上下文——前沿 LLM 确实有这个能力，但代价是什么？更多的幻觉和更高的 token 消耗。团队提出的假设是：能否给 LLM 装备一个智能导引（GPS），让 agentic AI 在工作流核心执行时产出更理想的结果？他们通过在四个 IBM 产品中设计和构建配备 agent logic 的 agent 来验证这个假设，这些产品覆盖了企业软件交付生命周期中一些最具挑战性的任务。

Numerous studies have cited the overwhelming failure of AI pilots, while others have also highlighted the need for AI to operate at the core of enterprise workflows to enable scalable adoption. To better understand this phenomenon and the associated assertion, some analysis of enterprise workflows is required. These workflows are: A. Dynamic and long-running B. Possess a plethora of APIs, databases and services C. Oftentimes are constrained by business policies and/or regulations

For an agent to function effectively, given these above characteristics, naturally demands an expanded model context, which state-of-the-art frontier LLMs certainly possess, but at what tradeoff? Increased hallucinations, token consumption? Further, can LLMs be equipped with an intelligent guide, GPS, to enable agentic AI execution at the core of the workflow, driving more desirable outcomes? We tested these hypotheses by designing and building agents, equipped with pertinent agent logic, for IBM offerings fully considering the above characteristics.

团队在四个 IBM 产品领域验证了 agent logic 的效果，涵盖企业软件交付生命周期的关键环节。遗留代码理解（WCA4Z）：利用深度静态分析和预索引数据库，在百万行级 COBOL/PL1 应用上保持接近的理解精度，同时 token 消耗降低约 30 倍。测试生成（Aster）：通过程序分析输出引导 LLM，在 75+ 个 Java 应用上实现 20-45% 的覆盖率提升，token 消耗比同类最先进编码 agent 低最多 15 倍。事件响应（I3 Agent）：用知识图谱和可观测性数据驱动的编排，在 ITBench 上实现比 ReAct agent 高 4.0 倍的表现。合规自动化：多 agent 系统通过算法分解和自适应规划，将成功率从个位数提升到 80% 以上。每个用例的核心模式都是一样的：用 agent logic 缩小 LLM 的上下文空间，引导它走对的路。

核心模式：
简化上下文，导航核心流程

纵观所有六个验证场景——四个产品用例和两个案例研究——一个统一的模式浮现出来：agent logic 通过在 agentic 层引入领域特定的软件原语，将 LLM 需要处理的上下文空间大幅缩小，同时精准引导它穿越企业工作流的核心路径。具体来说，知识图谱为事件响应提供了结构化的实体关系网络，程序分析库为代码理解和测试生成提供了预索引的精确信息，算法分解和自适应规划为合规自动化提供了协调的多步骤执行框架，而 policy-as-code 为医疗场景提供了运行时治理保障。这些原语的共同点在于：它们不是替代 LLM，而是给 LLM 装上了一个聪明的 GPS——告诉模型该看什么、该忽略什么、该沿着哪条路走。结果是：更高的精度、更低的 token 消耗、更少的幻觉，以及因此而来的用户信任。

可扩展采用的前提：
不是更大的模型，是更好的导引

几个世纪以来，人类受益于各种导引——从太阳到 GPS——它们简化了我们的生活并扩展了我们的能力。随着技术的演进，导引工具也在进化，让我们能做更多事情、进一步缩小地球村的距离。在这个 agentic AI 时代，当我们寻求通过规模效应进一步提升社会效能时，应该延续这个趋势：充分利用 agent logic 来简化模型上下文，智能地穿越企业工作流的核心。文章的结论明确而有力：只有这样，以最优运营成本实现真正可扩展的采用才具有可行性。这不是一个关于「大模型 vs 小模型」的争论——而是关于有没有给 AI 一个好的 GPS的问题。数据表明，配备 agent logic 的系统在精度、成本和可信度上全面胜出，而这正是企业大规模落地所需要的。

代码理解与测试生成：
程序分析的威力

遗留代码理解（WCA4Z）：IBM watsonx Code Assistant for Z 的 App Insights agent 利用深度静态分析遍历整个应用程序，并将预索引的表示存储在跨越数百个相互关联的表的数据库 schema 中。这使得 agent 能够检索精确的、结构化的、已有的信息，从而提高回答准确率、减少 token 使用，并最大限度减少与语言模型（此例中为 Mistral Medium 250B）的反复交互。当应用于多个关键任务遗留系统（最多 100 万行代码和 1,000 个程序）时，这种方法保持了略优于基线的应用理解性能，同时 token 消耗降低约 30 倍。测试生成（Aster）：Aster 是 IBM 专有的程序分析和数据前后处理库，用于基于 agent 的单元测试、集成测试、API 测试和变更测试生成。在 75+ 个 Java IBM CIO 应用（最多 560+ 个类和 67,000+ 行代码）上使用 Devstral 24B 模型运行，稳定结果显示行/分支/方法覆盖率提升 20-45%，与最先进的编码 agent 相比，在子集应用上表现更优，同时 token 消耗低最多 15 倍。其原理在于：程序分析输出用来聚焦 LLM 的 prompt，加上用于增强覆盖率和修复运行时/编译错误的 sub-agent，实现了更高性能和显著成本降低的双重效果。

IBM watsonx Code assistant for Z (WCA4Z), used to accelerate mainframe application development and modernization with AI and automation, is equipped with an App Insights agent for application understanding - one of the primary focus areas of enterprise clients running mission critical workloads on IBM mainframe. This agent leverages deep static analysis across the application and stores a pre-indexed representation in a database schema that spans hundreds of interrelated tables with complex semantics, allowing the agent to retrieve precise, structured already available information; thereby improving answer accuracy, reducing token usage, and minimizing back-and-forth interactions with the language model (Mistral Medium 250B in this instance). This approach when applied to multiple mission-critical legacy systems (up to 1M lines of code and 1K programs) maintains marginally superior app understanding performance with ~30x lower token consumption than a baseline frontier LLM-only approach.

Aster is an IBM proprietary program analysis and data pre- and post-processing-based library utilized for agent-based generation of unit, integration, API and change-based tests; which from analysis of multiple developer communities achieves higher developer ratings compared with various open-sourced tools or developer-written tests. Based on the latter and superior line, branch and method coverage benchmarks compared with similar open-sourced tools (integration tests) and zero-shot LLMs and coding agents (unit tests), all tested on open-sourced applications, we have been running Aster in pre-production mode on 75+ java IBM CIO applications (up to 560+ classes and 67K+ lines of code) with Devstral 24B model. Steady-state results to date yield +20% - 45% improvement in line, branch and method coverage coupled with superior performance on a subset of these apps compared with state-of-the-art coding agent with orders of magnitude lower token consumption (up to 15x).

事件响应与合规自动化：
知识图谱与自适应规划

事件响应（I3 Agent）：与代码相关的用例不同，运行时管理需要覆盖整个 IT 全栈。团队定义了一个知识图谱（KG），包含微服务、数据库/中间件服务、MELT 等实体，以及来自领域专家的嵌入式「部落知识」。通过将 LLM 限制在局部推理范围内处理非确定性结果，并使用可观测性驱动的方法，实现了跨 IT 栈和底层应用源代码的上下文空间缩减。在 ITBench 上，I3 agent 比 ReAct agent（GPT-5.1）实现了 4.0 倍的改善。团队还将此方法扩展到源代码分析（利用程序依赖图）和 bug 修复（利用推理扩展），在查找罪责微服务时实现了 3.0 倍的提升，同时分别消耗 3.7 倍和 5.9 倍更少的 token。合规自动化：企业面临日益复杂和碎片化的合规要求。团队构建的多 agent 系统通过算法分解将复杂任务拆分为协调步骤，使用自适应规划、动态分解和带持续反馈的工作流排序来迭代识别修复方案。该系统比使用固定规划策略的先前 agent（Claude 4 Sonnet）性能高 1.3-2.0 倍，并将成功率从个位数提升到 80% 以上。

While LLM context for app-related use cases as described in 1 and 2 are "restricted" to the app source code, for runtime management of apps on deployed infra, the underlying IT full stack comes into play. Here we define a knowledge graph (KG) encompassing entities (microservices, database/middleware services, MELT etc.) coupled with embedded ("tribal") knowledge from domain experts. With such a graph and bounding the LLM to local bound reasoning for non-deterministic outcomes, an observability-driven approach is used to achieve reduced context space spanning the IT stack and underlying app source code (if relevant) for incident root cause analysis (and other use cases). With this approach, leveraging the equivalent Instana data model, we have seen the proprietary Instana "I3" (intelligent incident investigation) agent achieve up to 4.0x improvement over ReAct agent with GPT-5.1 as measured using ITBench.

Enterprises face increasingly complex and fragmented compliance requirements, forcing teams to spend considerable time manually creating controls, assessments and remediation plans. No centralized knowledge exists and fixes are written manually, which introduces a risk of errors and security gaps. Because compliance work is complex and multi-step, it requires coordinated policy-driven automation across specialized agents rather than manual effort or simple AI prompts. Our multi-agent system automates compliance by algorithmically decomposing complex tasks into coordinated steps, using adaptive planning, dynamic decomposition and workflow sequencing with continuous feedback to iteratively identify fixes and expand assessments. It is 1.3 – 2.0x more performant than prior agents (Claude 4 Sonnet) using fixed planning strategies, as also measured using ITBench. This approach transforms compliance into a continuously guided self-correcting process and dramatically improves outcomes, especially in complex scenarios, boosting success rates from single digits to as high as +80% (Claude 4 Sonnet).
