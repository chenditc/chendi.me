ACT I — 军备竞赛

每个新模型，
都击败了我们的面试题

Anthropic的性能优化团队有一道著名的take-home面试题：候选人需要在一个模拟加速器上优化代码。超过1000人做过这道题，几十位工程师因此被录用——包括那些后来负责Trainium集群调优、参与了从Claude 3 Opus到最新每个模型发布的核心工程师。但问题是：每次发布新模型，这道题就得重新设计。因为Claude Opus 4在4小时时限内超过了大多数人类候选人，而Claude Opus 4.5在2小时内就追平了最强的人类表现。出题者Tristan Hume已经迭代了三个版本，每次都学到了新的东西：什么样的考核能抵挡住AI，什么样的不能。

原文

Since early 2024, our performance engineering team has used a take-home test where candidates optimize code for a simulated accelerator. Over 1,000 candidates have completed it, and dozens now work here, including engineers who brought up our Trainium cluster and shipped every model since Claude 3 Opus.

But each new Claude model has forced us to redesign the test. When given the same time limit, Claude Opus 4 outperformed most human applicants. That still allowed us to distinguish the strongest candidates—but then Claude Opus 4.5 matched even those.

好的面试题长什么样？

Tristan的设计目标和大多数take-home完全不同。大多数take-home充满了无聊的通用题目，既不好玩也筛不出人。他的目标是做一道让候选人兴奋到停不下来的题：4小时时限到了还想继续做。具体原则包括：必须代表真实工作——候选人做题时就能感受到这份工作的样子；必须高信号——避免单一洞察力决定成败，给候选人多次展示能力的机会；不要求特定领域知识——基础扎实的人入职后能学会细节；最后也是最重要的：好玩——快速开发循环、有深度的有趣问题、发挥创意的空间。

原文

Take-homes have a bad reputation. Usually they're filled with generic problems which engineers find boring, and which make for poor filters. My goal was different: create something genuinely engaging that would make candidates excited to participate and allow us to capture their technical skills at a high-level of resolution.

Representative of real work: The problem should give candidates a taste of what the job actually involves. High signal: The take-home should avoid problems that hinge on a single insight and ensure candidates have many chances to show their full abilities. No specific domain knowledge: People with good fundamentals can learn specifics on the job. Fun: Fast development loops, interesting problems with depth, and room for creativity.

ACT II — 原始设计

一台假的加速器，
一道真的优化题

Tristan用Python写了一个模拟加速器——特征酷似TPU：手动管理的暂存内存（不像CPU自动缓存，加速器要求你显式管理数据搬运）、VLIW超长指令字（多个执行单元每个时钟周期并行运行，需要高效的指令打包）、SIMD向量操作、以及多核心。任务是并行树遍历——故意不选深度学习方向，因为大多数性能工程师入职时并没有深度学习经验。候选人从一个完全串行的实现开始，逐步挖掘机器的并行性。最强的无限时间提交甚至包含了完整的迷你优化编译器和Tristan没预料到的巧妙优化。

原文

I built a Python simulator for a fake accelerator with characteristics that resemble TPUs. Candidates optimize code running on this machine, using a hot-reloading Perfetto trace that shows every instruction.

The machine includes features that make accelerator optimization interesting: manually managed scratchpad memory, VLIW (multiple execution units running in parallel each cycle), SIMD (vector operations on many elements per instruction), and multicore (distributing work across cores).

The task is a parallel tree traversal, deliberately not deep learning flavored. Candidates start with a fully serial implementation and progressively exploit the machine's parallelism.

原文

When I tested a pre-release Claude Opus 4.5 checkpoint, I watched Claude Code work on the problem for 2 hours, gradually improving its solution. It solved the initial bottlenecks, implemented all the common micro-optimizations, and met our passing threshold in under an hour.

Then it stopped, convinced it had hit an insurmountable memory bandwidth bottleneck. Most humans reach the same conclusion. But there are clever tricks that exploit the problem structure to work around that bottleneck. When I told Claude the cycle count it was possible to achieve, it thought for a while and found the trick.

By the 2-hour mark, its score matched the best human performance within that time limit—and that human had made heavy use of Claude 4 with steering.

ACT III — 反击

尝试一：数据转置
——Claude找到了意外解法

Tristan选了一个他在Anthropic做过的最棘手的内核优化问题：在2D TPU寄存器上做高效的数据转置，同时避免bank conflict。他把这个问题简化后做成新题，Claude帮他一天之内就实现了。但Claude Opus 4.5做出了一个他从没想过的优化：通过仔细分析，它意识到可以转置整个计算过程而不是转置数据本身——整个程序被重写了。Tristan堵上了这条路之后，Claude一开始确实做不出最优解。但当他用Claude Code的「ultrathink」模式给更长的思考预算时，它又解出来了——它甚至知道修复bank conflict的技巧。回想起来，这不是个好选择：太多工程师在不同平台上都跟数据转置和bank conflict较劲过，Claude有大量训练数据可以借鉴。

原文

I chose a problem based on one of the trickier kernel optimizations I'd done at Anthropic: an efficient data transposition on 2D TPU registers while avoiding bank conflicts.

Claude Opus 4.5 found a great optimization I hadn't even thought of. Through careful analysis, it realized it could transpose the entire computation rather than figuring out how to transpose the data, and it rewrote the whole program accordingly.

I patched the problem to remove that approach. Claude then made progress but couldn't find the most efficient solution. But I had some nagging doubt, so I double-checked using Claude Code's "ultrathink" feature with longer thinking budgets ... and it solved it.

In hindsight, this wasn't the right problem to try. Engineers across many platforms have struggled with data transposition and bank conflicts, so Claude has substantial training data to draw on.

尝试二：Zachtronics谜题
——终于赢了

Tristan需要的是一种人类推理能赢过Claude庞大经验库的问题——足够离谱、足够out of distribution。他想到了Zachtronics编程解谜游戏：这些游戏使用极度受限的指令集，迫使你用非常规的方式编程。比如在Shenzhen I/O里，程序被分散到多个通信芯片上，每个只能存10条指令和一两个寄存器。他设计了一组使用极简受限指令集的谜题，优化目标是最少指令数。而且他故意不提供可视化和调试工具——判断是否值得投入时间自建工具本身就是在考察能力。Claude Opus 4.5做不出来。同事们验证了人类确实能超过Claude。Tristan对新题比较满意，但也感慨：「现实性可能是我们已经负担不起的奢侈品了」。原来的题之所以好用，是因为它像真实工作；新题之所以好用，是因为它模拟了全新的工作。

原文

I needed a problem where human reasoning could win over Claude's larger experience base: something sufficiently out of distribution.

I thought about the most unusual optimization problems I'd enjoyed and landed on Zachtronics games. These programming puzzle games use unusual, highly constrained instruction sets that force you to program in unconventional ways.

I designed a new take-home consisting of puzzles using a tiny, heavily constrained instruction set, optimizing solutions for minimal instruction count. I implemented one medium-hard puzzle and tested it on Claude Opus 4.5. It failed.

I'm still sad to have given up the realism and varied depth of the original. But realism may be a luxury we no longer have. The original worked because it resembled real work. The replacement works because it simulates novel work.

ACT IV — 公开挑战

三个版本，三次溃败

这道面试题的历史就是一部AI军备竞赛的缩影。2023年11月，Tristan设计了V1——为了给即将到来的Claude 3 Opus训练和新集群做准备而大规模招人。V1运行了一年半，成功筛选了1000+候选人。但到2025年5月，Claude 3.7 Sonnet已经让超过50%的人类候选人表现不如直接用AI。于是他设计了V2：用Opus 4找到它开始挣扎的地方作为新起点，移除多核（Claude已解决的部分），增加新机器特征，时间从4小时缩到2小时。V2强调巧妙的优化洞察力而非调试能力和代码量。这个版本扛了几个月——直到Opus 4.5测试版在2小时内追平了最强人类。

原文

In November 2023, we were preparing to train and launch Claude Opus 3. We needed a way to evaluate candidates more efficiently. So, I took two weeks to design a take-home test.

Over the next year and a half, about 1,000 candidates completed the take-home. By May 2025, Claude 3.7 Sonnet had already crept up to the point where over 50% of candidates would have been better off delegating to Claude Code entirely.

For the take-home, there was a straightforward fix. I used Claude Opus 4 to identify where it started struggling. That became the new starting point for version 2. I wrote cleaner starter code, added new machine features for more depth, and removed multicore. I also shortened the time limit from 4 hours to 2 hours. Version 2 emphasized clever optimization insights over debugging and code volume.

为什么不禁用AI？

面对Opus 4.5即将击败面试题的现实，有同事建议直接禁止AI辅助。Tristan不想这么做。除了执行难度，他有一个更深层的信念：既然人在实际工作中仍然扮演关键角色，那他应该能找到某种方式，让人在有AI辅助的环境下依然能区分出来——就像他们在真实工作中一样。他还不想向「人类只在超过几小时的任务上才有优势」这个观点投降。另一个建议是「要求大幅超过Claude单独完成的水平」，但问题是Claude工作太快了——人类通常要花一半时间读题理解问题才开始优化，而试图引导Claude的人总是在追赶、只能事后才理解Claude做了什么。主导策略可能变成坐着看。如今Anthropic的性能工程师仍有大量工作，但更像是调试、系统设计、性能分析、验证正确性——这些很难在客观的短时考核中测量。

Some colleagues suggested banning AI assistance. I didn't want to do this. Beyond the enforcement challenges, I had a sense that given people continue to play a vital role in our work, I should be able to figure out some way for them to distinguish themselves in a setting with AI—like they'd have on the job.

Others suggested raising the bar to "substantially outperform what Claude Code achieves alone." The concern here was that Claude works fast. Humans typically spend half the 2 hours reading and understanding the problem before they start optimizing. A human trying to steer Claude would likely be constantly behind. The dominant strategy might become sitting back and watching.

Nowadays performance engineers at Anthropic still have lots of work to do, but it looks more like tough debugging, systems design, performance analysis, figuring out how to verify the correctness of our systems.
