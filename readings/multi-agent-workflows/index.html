Failure Surface

一旦从单 agent 变成多 agent，新增的不是“更多能力”，而是更多失败面。

团队会在端到端问题太复杂时引入多 agent，例如代码库维护、依赖更新、质量检查、重构、按规格实现功能、issue 和 PR 分流。但这些场景只有在每一步都显式且受约束时才可靠；否则共享状态、顺序假设、隐式交接和非确定性行为会一起放大。

What multi-agent systems are

文章列举了代码库维护、自动质量检查、重构、spec-driven implementation、issue/PR triage 等使用场景，并强调引入多个 agent 会同时引入共享状态、顺序和交接问题。

Three Contracts

可靠性来自三层约束：数据格式、行动意图、工具接口。

文章给出的解法不是“把 prompt 写得更长”，而是把 agent 间的软沟通改成硬边界。typed schemas 约束数据长什么样，action schemas 约束下一步能做什么，MCP 或类似层负责在工具执行前把这些约束真正 enforce。

Article structure

正文主体分成三节：typed schemas、action schemas、MCP。三节分别回答“传什么数据”“允许什么行动”“谁来执行前校验”。

Typed Schemas

自然语言会漂移，typed schema 把交接变成机器可检查的合同。

多 agent 早期失败常常很朴素：字段名变了、类型对不上、JSON 格式摇摆、下游步骤只能猜 payload 的意思。typed schema 的作用，是让每个边界都有可验证的数据形状；一旦数据无效，系统应该重试、修复或升级，而不是让坏状态继续传播。

Debugging

schema 的价值不只是防错，而是把调试问题改写成“哪个合同失败了”。

没有结构时，工程师只能回看日志，猜 agent 当时为什么这么做。有 schema 后，错误能落到具体边界：某个 payload 违反了某个字段、类型或枚举。因为失败变得可定位，所以系统才能在坏状态进入下游前做 retry、repair 或 escalate。

Contract failure framing

typed schemas 一节强调 schema violation 应被当作 contract failure，处理方式包括重试、修复或升级，目标是在坏状态传播前拦住它。

Action Schemas

即使数据结构正确，行动意图仍然可能是模糊的。

“分析这个 issue 并帮助团队采取行动”听起来合理，但对不同 agent 来说，关闭、分配、升级、不处理都可能合理。action schema 的意义，是把开放式意图收束成一小组明确、互斥、可验证的行动；最终结果必须落到其中一个合法 action。

action schemas 一节用 issue 处理场景说明：开放指令会导致多个“看似合理但不可自动化”的结果，所以必须定义允许行动集合。

MCP Enforcement

没有 enforce 的 schema 只是约定；MCP 把约定变成执行前的门。

typed schemas 和 action schemas 只有被持续执行才有意义。文章把 MCP 描述为 enforce layer：每个 tool 和 resource 都有输入输出 schema，调用在执行前就被验证。这样 agent 不能随手发明字段、漏掉必填项，错误也不会先打到生产系统再被发现。

Principles

最后的原则很简单：把 agent 当代码，而不是当聊天窗口。

文章收束成一组系统设计原则：先为失败设计，验证每个 agent 边界，在增加 agent 前先约束行动，记录中间状态，并预期重试和部分失败。因为多 agent 系统会像分布式系统一样失效，所以可靠性也必须用分布式系统的方式设计。

✓ 先为失败设计
✓ 验证每个边界
✓ 先约束行动
✓ 记录中间状态
✓ 预期部分失败
Agents as code
这不是“多放几个 agent”的问题，而是先把边界、契约和可观测性补上，再让 agent 接管流程。

Contract Design

typed schema 要落在“边界”上，而不是只写在文档里。

最关键的设计动作，是先画出 producer 和 consumer：哪个 agent 产出 profile、triage result、patch plan 或 check result，哪个下游步骤消费它。只要结果会被另一个组件读取，就应该有 schema、required field、enum、nullable 语义和错误形状，否则下游仍然会被迫猜。

Typed interfaces

文章把 typed interfaces 类比为开发中的合同：合同越早建立，协作越少互相踩脚。这里把它转成边界设计方法。

Failure Handling

schema 失败不是异常噪音，而是工作流的一条正式分支。

如果 contract failure 只被记录但不改变流程，那么坏数据仍然会继续流动。更稳的做法是为每个边界定义 retry limit、repair prompt、升级路径和停止条件。这样系统遇到无效 payload 时，会进入可控的修复流程，而不是让下游 agent 拿着脏数据继续推理。

Retry, repair, escalate

typed schemas 一节明确说 schema violations 应该在坏状态传播前重试、修复或升级。这里把它做成可执行的失败分支。

Action Union

action schema 最好是小而硬的 discriminated union。

文章示例里，行动不是自由文本，而是 request-more-info、assign、close-as-duplicate、no-action 这样的枚举分支。这个结构迫使 agent 选择一个动作，并携带该动作必需的字段。因为每个动作的字段不同，所以 discriminated union 比“一个大对象加可选字段”更不容易被误用。

Tool Boundary

MCP 最重要的时机，是工具执行之前。

如果验证发生在工具已经修改 issue、发出评论或创建 PR 之后，错误就已经变成了外部状态。MCP 的价值在于把 input_schema 和 output_schema 放在调用门口：输入不合格就不执行，输出不合格就不进入下一步。于是“错误调用”不会先污染生产系统。
