后龙虾时代：
Agent 从「能用」到「生产级」

过去一段时间，OpenCloud热潮席卷全网——全民养龙虾、装Claude、周末给业务团队做培训。但顺丰集团CIO刘潭仁总结得精准：「一虾掀起千层浪」，技术突破只是基础，更重要的是大众对AI认知发生了质变。然而，从个人场景「看上去很酷」到企业生产环境「真正能用」，中间隔着一段很长的距离。这场由InfoQ创始人Kevin主持、顺丰CIO刘潭仁和深信服CIO宋东林参与的深度对话，正是要找到这段距离的答案——怎么让Agent在企业里面是能用的、好用的、不翻车的。

过去一段时间的话，OpenCloud 是非常火的，全民都在去养龙虾。很多人在自己的私人的场景里面，其实是在使用的，但是真正到工作场景里面去使用的时候，就会遇到蛮多的问题。所以说在我看来，当下从看上去很酷，到真正 Agent 在企业里面去使用，其实是有一个非常长的一段距离的。

我自己总结是一虾掀起来千层浪，其实技术上的突破，它只是一个基础。更多的是说大众对这个 AI 的认识会发生一个变化，就是形态让他看到了这个未来是什么样子。

这一次我们是不去谈特别多的概念性的东西，而是去谈 AI 到底在企业里面怎么去落地，怎么让 Agents 在企业应用的过程里面是能用的，好用的，怎么是不翻车的。

双雄实战：
顺丰人资 × 深信服研发

顺丰和深信服走了两条截然不同的路径。顺丰在人力资源场景发力，用Agent端到端接管新员工入职的全流程——从信息采集到签合同再到各类服务，原本需要专人跟进的工作现在由智能体完成。他们还用OpenCloud这种方式解决客户智能体中长尾的、不确定性的问题，因为传统APP的固定交互没法穷举所有场景。深信服则在研发场景探索出多Agent协作对抗的模式：一个Agent写代码，另一个Agent做测试，它们用不同的模型和策略互相博弈，在对抗中让代码质量持续提升。这不是单点工具的替代，而是整个研发旅程的Agent化——从需求到设计到编码到测试到上线，都是不同Agent在接力。

四维选场景：
ROI · 技术 · 数据 · 认知

顺丰选择Agent落地场景有四个核心维度。第一是ROI——规模大才值得投入，先能尝到甜头。第二是技术适配度，因为大模型有自己的特点，不同阶段的主要矛盾也不同。第三是数据和知识的准备度，你不可能在没有基础的情况下突然起来一个Agent。第四是业务认知成熟度，业务领导必须认可这件事、愿意推动，整条线才能跑通。深信服的宋东林补充了不同行业的差异：金融看重智能问数和合规检测，制造业聚焦降本增效和产线运维，医疗行业则从早期的病例整理演进到了临床决策辅助。核心逻辑是一样的——高频且痛的场景、企业能支持的投入度、以及数据准备的成熟度。

其实行业里面有标准的说法，海量重复，然后又复杂的场景。其实这个大的逻辑其实没什么问题。所以我们其实沿用这个逻辑，我去看几个东西。第一呢，ROI。这个是很重要的，因为从投资的角度来看，规模大，那做这个事情就有意义。第二呢就是技术的适配度，大部分有自己的特点，并不是说所有东西都能够解决。第三个其实我们还关注数据和知识的准备度，你不可能在数据知识没有一个基础的情况下，能够突然起来一个 Agent。

还有一个成熟度，业务他对这个事情要有认知，有一个协同的统一的一个战略去看这个事情，这个事情大家都想改变。那自然他就会优先做，或者业务的领导觉得这个事情很重要，他愿意去推，他自然整条线下来就会好很多。

比如说像金融比较关注于智能的问数，因为它有海量的数据，想深挖数据背后的根因。制造业的客户，他的毛利率是很薄的，他们很关注降本增效。像医疗行业，早些年像病例的整理、基本的问答，但这几年随着医疗的信息化水平的提升，更多的 AI 来帮助医疗企业在做决策。

灵活 vs 可控：
问数的失败教出的智慧

智能问数曾是最火的场景，但顺丰做了才发现它「不一定是个真实需求」——用户问一两次就不再问了，推一波用户量多一波，不推就掉下去。转变的关键在两步：第一步是收敛数据，用面向对象的大宽表把核心数据和元数据整理好；第二步更关键——把分析师的专家经验固化为skill，让智能体不仅能问数，还能搭建分析报表、做归因分析、出解决方案。用户发现这个东西能帮他解决大部分工作量，留存率就慢慢起来了。这背后是两个关键的平衡：灵活性与可控性——在规则内保留灵活性，但关键套路必须固化；准确性与用户接受度——「跟人比，不跟神比」，只要价值大、用户觉得划算，90%的准确率就够了。

原文

大家知道智能问数，这前几年其实都很火。这个事情呢，其实我们一开始做的时候还是用传统的方式去做，发现做出来，它的准确率呢，在百分之八九十就算比较高了。问数这个场景呢，它不一定是个真实需求。很多人问一次问两次，他就不再问了。你推一波，他就用户量多一波，不推他就会掉下去。

后来为了解决这个问题，改变了一个思路。第一个就是把后台的数据范围更固定，做面向对象的数据格式，大宽表的方式把所有核心数据和元数据全都整理得好好的。第二个很重要的点是我们把用户分析的这些经验变成 skill，放在智能体里面去了。不仅问数，还能给他搭建分析报表、分析报告，还可以做归因分析，还给他出解决方案。

本质上它是个智能，你要跟人比。我们的逻辑说，你始终要解决问题，人其实也会犯错的。所以智能体这个东西，你不要跟神比，你要跟人比。如果说你跟人比，你就会发现很多事情，人做的报表和分析逻辑和解决方案，还没有那个智能体出来的好。

知识五级：
从 L1 培训到 L5 智能体

顺丰把知识管理分为五个层级：L1是培训课程，L2是问答机器人QNA，L3是陪练帮助员工快速成长，L4是在业务流关键环节提供操作指引，L5是直接把知识喂给智能体。前四个层级都是面向人的——培训人、回答人、陪练人、指导人。但L5发生了质变：知识不再经过人的理解和执行，而是直接驱动智能体行动。这意味着知识管理体系必须跟着变——不仅要输出对人的知识，还要同时输出对AI的知识。Skill本身也成为了知识的一部分。企业的核心竞争力取决于你的业务场景以及你的数据和知识，这件事要当做战略来看。

坐电梯不造电梯：
技术路线与避坑

技术路线的选择，刘潭仁的答案很干脆：「坐电梯，不造电梯。」技术迭代太快，企业自建基座模型不现实，更聪明的做法是把精力放在自己的场景、数据和知识上。宋东林用了一个精彩的比喻：平台是船，知识是船上的货物，大模型是水——大部分企业应该买船而不是造船，然后关注怎么让水位（模型能力）把船抬得更高。回顾过去一两年，两位CIO最大的遗憾是：不应该花那么多成本训练垂域模型——应该先用prompt调到极限，调到不能调为止，再考虑别的；以及应该从一开始就从端到端的业务流思考，而不是只看单点环节。因为Agent有主动规划和主动思考的能力，正好迎合了端到端的需求。

技术发展很快，现在还没有到一个相对来说的稳态。我们不会去束缚大家用什么样的工具。更多是说怎么快速地准备好，然后能够乘电梯往上走。我们现在是算法应该是50%依靠行业里面最先进的模型去做，算力的资源基本上都是用云上最好的资源。其实我要做的事情就是把我的场景理清楚，把我的数据搞明白。

有一个比喻还挺有意思的，假设说有一艘船，那个船就是你的平台。平台上面承载的其实是你的知识。船底下的水呢，其实是不同的先进的大模型。以前大家会集中很多资源去造这个船，现在其实有很多选择，可以直接去买一艘船。你关注的点不应该在船上面，应该在你上面的知识上面。

前两年面临一个很难的抉择，是要持续训练自己的垂域模型，还是坐船坐电梯。今天的经验来看，大部分的企业，先考虑用 prompt 或者用业界最好的模型，你到底能调到一个什么效果？调到不能调为止。再去考虑别的。

如果说再来一遍，我个人觉得一开始就应该思考的是不要只看作一个单点的环节，而是端到端的业务流程，才有可能真正让这个事情发生质变。这是一个 AI 觉醒的时代。赶紧上船，赶紧造好自己的船。

顺丰销售智能体：
360画像的多智能体协同

顺丰在26年之前已经用AI做了大量单点优化——APP一句话下单、客服自动接电话填单结案、理赔自动审核、小哥机器人辅导。但26年Agent浪潮来了之后，他们开始探索全面拥抱Agent的方式。一个典型案例是销售智能体：一线销售去拜访客户时，智能体会告诉他客户的360度全景信息——之前开过的会议、拜访结果、合作情况、服务履约状况。关键在于，这些信息来自多个不同的智能体协同：运营数据来自履约智能体，客户信息来自客户智能体，销售智能体协同各方，让一个新销售瞬间变成「老销售」。这就是Agent的核心价值——不是替代某个环节，而是协同多个数据源解决一个完整的业务场景。

在我们的 APP 里面，你是可以一句话或者是一张图下单的。客服其实可以自动接电话，自动回答问题，也可以自动填单，甚至自动结案。还可以理赔，做理赔的一些自动审核。在小哥环节，我们也原来做的类似 QNA 的小哥机器人去帮助小哥解决日常的一些问题。

深信服多Agent对抗：
coding × testing 的进化

深信服在研发场景的探索超越了简单的AI编程工具。宋东林指出，Cursor、Copilot这类工具解决的是「用AI生成代码」这个单点需求，但他们探索出了更好的形式——多个Agent做协作和对抗。比如一个生成代码的Agent和一个做测试的Agent，它们可能用不同的模型、不同的策略，在不断对抗中让代码质量和风格变得更好。而且这不止于coding和testing——整个研发全旅程都被Agent化：需求变成设计文档、设计文档变成代码、代码测试、部署上线，每个环节都有不同的Agent。中间还有对抗环节，比如设计文档出来后有评审Agent检查是否符合需求、是否完善、有没有风险。Agent们在互相对抗中成长、进化。

原文

其实有一个场景还是挺有意思的，就是 AI coding。现在很多人都有在用 Cursor、Copilot 之类的编程工具，但是经过我们研发同学探索发现有一种更好的使用方式。因为 Cursor 或者 Copilot，他们解决的是通过 AI 去生成代码的单点需求。

其实我们会探索出更好的形式，就是多个 Agent 去做协作和做对抗。比如说同样的生成代码的 Agent 和一个做测试的 Agent，他们互相之间是有对抗和协作关系的。他们两个可能本身就是不同的模型，然后也会有不同的策略，通过不断地对抗让代码质量和风格变得更好。

整个研发的全旅程，包括需求怎么变成设计文档，设计文档怎么变成代码，代码怎么进行测试，怎么部署上线，都是不同的 Agent 的。并且中间还有对抗的环节，比如设计文档出来了，有另外一个评审的 Agent 来检查设计文档到底符不符合需求，有没有什么风险，他们在互相对抗中来成长，来进化。

冲突与去重：
AI知识库的两大治理痛点

宋东林分享了对AI知识管理两个特别痛的问题。第一个是冲突知识：同一个问题在2015年和2025年的答案可能完全不同，但知识库是沉淀历史的过程，所以不同来源的知识可能互相矛盾。模型遇到冲突就会困惑——不知道该选谁，随便选一个就很容易出错。解决方法是用AI对知识库做一遍治理，识别并剔除冲突的知识。第二个是重复问题：知识库越大不一定越好，因为大量重复信息会导致密度很低，模型检索效率也低。解决方法是提前做重复识别和一键清理。此外，持续学习也很关键——在使用过程中标记good case和bad case，基于标签来净化知识库和优化prompt，让Agent「越用越聪明，越用越懂你」。

原文

对 AI 的知识来说，有两个比较痛的问题。第一个痛的问题是 AI 其实是不能接受冲突的知识的。比如说同样的一个问题，可能在2015年的答案是这样子，但是在2025年、2026年的今天，答案又不一样了。因为我们的知识库是沉淀历史的过程，所以可能会存在一个知识在不同的来源里面是冲突的，模型就会困惑，不知道该选谁，随便选一个，就很容易就会错了。

我们现在其实是完全可以利用 AI 去把知识库做一遍治理来识别出里面冲突的知识，把不对的知识剔除掉之后，通常来说效果会提升一些。

另外还有一个关于重复的识别。知识库如果越大，它不一定是越好的。因为里面大量的信息如果是重复的，对我们来说是叫密度很低，模型检索起来效率也很低。提前做一个识别，把重复的知识标记出来，一键去做清理。

希望我们的 Agent 能具有持续学习能力之后，它能够越用越聪明，越用越懂你。在使用过程中可以给它打一个标记，比如这个是一个好的回答叫 good case，这个是坏的回答 bad case。基于这个标签来自己净化自己的知识库。

从面向人到面向AI：
未来知识体系变革

原来的知识管理是面向人的——培训让人学习、QNA让人查询、操作指引让人照做。但AI时代出现了根本性的转变：知识需要同时面向人和AI。这不仅仅是格式的变化，而是整个信息系统架构的重塑。刘潭仁举了一个很直观的例子：原来的CRM系统之所以推不下去，就是因为要让人去录那些字段——那个时代的逻辑是技术只能处理结构化数据。但现在AI能处理结构化数据、非结构化数据、图片、视频、语音——应用的交互方式和处理数据的形态都发生了巨大变化。未来知识管理有没有可能不再需要人去沉淀，而是更多用AI自动处理？原来的数据中台只能处理结构化数据，但现在录的视频语音，AI就能提取出销售机会点。以人为主的知识体系一定会改变，整个业务流、信息流都会发生改变。

数据中台 → AI驱动的信息系统

以人为主的知识体系，一定会变成另外一个世界的信息系统。

原文

现在的知识管理体系，我们很多东西其实基于原来以人为基础建立的体系，包括应用形态也是这样子。原来应用很多是 system of record，就是个记录系统。你销售的系统，原来 CRM 为什么推不下去，很难用，就是因为你要让别人在录那些字段。那个时代是因为信处理的技术就只能处理这些数据。

现在不一样，现在是技术可以处理结构化的数据，也可以处理非结构化数据。包括图片、视频、语音全都能处理。可以肯定未来的应用形态，它的交互方式以及它处理的数据的形态发生巨大变化。所以应用本身数据和信息的组织方式就改变了。

未来知识有没有可能也变成了一个，我不需要人去沉淀，更多是用 AI 去帮忙做处理就可以了。以人为主的知识体系，它其实有可能会改变。就它一定会变成另外一个世界的信息系统。整个业务流、信息流都会发生改变。
