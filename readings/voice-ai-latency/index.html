语音 AI 要想让人觉得自然，对话节奏必须跟上真人说话的速度。一旦网络拖了后腿，用户马上就能听出来——尴尬的停顿、被截断的打断、延迟的插话。这对 ChatGPT 语音模式、Realtime API 开发者、以及需要在用户还在说话时就处理音频的模型来说，都是致命的体验问题。在 OpenAI 的规模下，这意味着三个硬性要求：全球覆盖9亿周活用户、快速建连让用户开口就能说话、以及低且稳定的往返延迟让轮替对话干脆利落。

Voice AI only feels natural if conversation moves at the speed of speech. When the network gets in the way, people hear it immediately as awkward pauses, clipped interruptions, or delayed barge-in. That matters for ChatGPT voice, for developers building with the Realtime API, for agents working in interactive workflows, and for models that need to process audio while a user is still talking.

At OpenAI's scale, that translates into three concrete requirements: Global reach for more than 900 million weekly active users Fast connection setup so a user can start speaking as soon as a session begins Low and stable media round-trip time, with low jitter and packet loss, so turn-taking feels crisp

The team at OpenAI responsible for real-time AI interactions recently rearchitected our WebRTC stack to address three constraints that started to collide at scale: one-port-per-session media termination does not fit OpenAI infrastructure well, stateful ICE and DTLS sessions need stable ownership, and global routing has to keep first-hop latency low.

WebRTC 把实时通信的所有难题都标准化了——AI 只需接上去就行

WebRTC 是一个开放标准，用于在浏览器、移动端和服务器之间传输低延迟的音频、视频和数据。它把交互式媒体中最困难的部分全部标准化了：ICE 负责连接建立和 NAT 穿透，DTLS 和 SRTP 负责加密传输，编解码器协商负责音频压缩，RTCP 负责质量控制，还有客户端的回声消除和抖动缓冲。如果没有 WebRTC，每个客户端都需要自己解决 NAT 穿透、媒体加密、编解码器选择等问题。而对 AI 来说，最关键的特性是音频以连续流到达——语音 agent 可以在用户还在说话时就开始转写、推理、调用工具或生成语音，而不是等一整段上传完毕。这就是「对话感」和「对讲机感」的本质区别。

WebRTC is an open standard for sending low-latency audio, video, and data between browsers, mobile apps, and servers. It's often associated with peer-to-peer calling, but it's also a practical foundation for client-to-server real-time systems because it standardizes the hard parts of interactive media: ICE for connectivity establishment and NAT traversal, DTLS and SRTP for encrypted transport, codec negotiation for compressing and decoding audio, RTCP for quality control, and client-side features such as echo cancellation and jitter buffering.

That standardization matters for AI products. Without WebRTC, every client would need a different answer for how to establish connectivity across NATs, encrypt media, negotiate codecs and adapt to changing network conditions. With WebRTC, we can build on a protocol stack that's already implemented across browsers and mobile platforms, focusing our own work on the infrastructure that connects real-time media to models.

We also build on the WebRTC ecosystem itself, including mature open-source implementations and the standard work that keeps browsers, mobile apps, and servers interoperable.

For AI, the most important property is that audio arrives as a continuous stream. A spoken agent can begin transcribing, reasoning, calling tools, or generating speech while the user is still talking, instead of waiting for a full upload. That's the difference between a system that feels conversational and one that feels like push-to-talk.

ACT II · 架构选择

多人会议用 SFU，但 1:1 语音AI 需要更直接的路径

选定 WebRTC 后，下一个问题是在哪里终结（terminate）连接、如何把会话接入推理后端。SFU（选择性转发单元）是多方通话的经典方案——它为每个参与者终结一条 WebRTC 连接，AI 作为另一个参与者加入。但 OpenAI 的场景不同：绝大多数会话是 1:1——一个用户对一个模型，或一个应用对一个实时 agent——而且每一轮对话都对延迟极度敏感。因此 OpenAI 选择了 Transceiver 模型：一个 WebRTC 边缘服务终结客户端连接，然后把媒体和事件转换成更简单的内部协议，分发给推理、转写、语音生成和编排服务。Transceiver 是唯一拥有 WebRTC 会话状态的服务，后端服务可以像普通服务一样扩展，不需要自己充当 WebRTC peer。

An SFU, or selective forwarding unit, is a media server that receives one WebRTC stream from each participant and selectively forwards streams to the others. In this model, the SFU terminates a separate WebRTC connection for every participant, and the AI joins as another participant in the session. That can be a good fit for products that are inherently multiparty, such as group calls, classrooms, or collaborative meetings.

Our workload is different. Most sessions are 1:1—one user talking to one model, or one application talking to one real-time agent—with latency sensitivity on every turn. For that shape of traffic, we chose a transceiver model: a WebRTC edge service terminates the client connection and then converts media and events into simpler internal protocols for model inference, transcription, speech generation, tool use, and orchestration.

In this design, the transceiver is the only service that owns the WebRTC session state, including ICE connectivity checks, the DTLS handshake, SRTP encryption keys, and session lifecycle. Keeping that state in one place made session ownership easier to reason about, and it let backend services scale like ordinary services instead of acting as WebRTC peers themselves.

每个会话一个端口的传统模型，在 Kubernetes 上彻底走不通了

选好 Transceiver 模型后，OpenAI 的第一版实现是一个基于 Pion 的 Go 服务，同时处理信令和媒体终结。但问题很快暴露了：传统 WebRTC 的「每个会话一个 UDP 端口」模型与 Kubernetes 环境严重冲突。高并发下需要暴露和管理大量 UDP 端口范围，而云负载均衡器和 K8s service 根本不是为成千上万个公共 UDP 端口设计的。更糟糕的是，大量 UDP 端口范围扩大了外部可达的攻击面，让网络策略审计变得困难。而且 Pod 在 K8s 中不断被添加、移除和重新调度，要求每个 Pod 预留大段稳定端口范围会让弹性伸缩变得脆弱。

After choosing the transceiver model, our first implementation was a single Go service built on Pion that handled both signaling and media termination. It powers ChatGPT voice, the Realtime API's WebRTC endpoint, and a number of research projects.

We wanted the service to run like the rest of our infrastructure: on Kubernetes, where workloads can scale up and down, and move across hosts as demand changes. But the conventional one-port-per-session WebRTC model fits that environment poorly, because it depends on large public UDP port ranges that are difficult to expose, secure, and preserve as pods are added, removed, or rescheduled.

Cloud load balancers and Kubernetes services are not designed around tens of thousands of public UDP ports per service. Each additional range adds operational complexity in load balancer config, health checking, firewall policy, and rollout safety.

Large UDP port ranges are hard to secure because they expand the externally reachable surface area and make network policy harder to audit.

They're also a poor fit for autoscaling. Pods are constantly added, removed, and rescheduled in Kubernetes. Requiring each pod to reserve and advertise a large stable port range makes that elasticity brittle.

ACT III · 解决方案

四种路径，只有一种能同时满足小端口面、会话粘性和弹性伸缩

OpenAI 评估了四种方案：最传统的「每会话一个端口」直接暴露——端口面大、K8s 不友好；「每服务器一个端口」能减少端口数，但在负载均衡的集群中仍无法保证首包路由到正确实例；TURN 中继能集中入口策略，但分配过程增加了建连往返，且跨服务器迁移困难。最终 OpenAI 选择了第四条路：无状态转发器 + 有状态终结器——也就是 Relay + Transceiver 的分离架构。Relay 只负责转发包，不解密、不运行 ICE 状态机、不参与编解码器协商；Transceiver 仍然拥有完整的 WebRTC 会话。这样既缩小了公共 UDP 暴露面，又保持了标准 WebRTC 行为。

We evaluated several ways to get there, including TURN, where an edge relay terminates client allocations and forwards traffic on their behalf.

Unique IP:port per session: Direct client-to-server media path, no forwarding layer. But requires one public UDP port per session, large port ranges difficult to expose and secure, poor fit for Kubernetes.

Unique IP:port per server: Much smaller public UDP footprint, one shared socket per server. But works cleanly on a single host only; across a load-balanced fleet, the first packet can still land on the wrong instance.

TURN relay: Clients only need to reach the TURN relay address and port, can centralize policy at the edge. But TURN allocations add setup round trips, moving or recovering allocations across TURN servers is still difficult.

Stateless forwarder + stateful terminator (OpenAI's relay + transceiver): Small public UDP footprint, transceiver still owns the full WebRTC session. Adds one forwarding hop, requires custom coordination between relay and transceiver.

把包路由和协议终结彻底分开——Relay 只转发，Transceiver 管状态

OpenAI 最终交付的架构把包路由和协议终结分成了两层。信令仍然直达 Transceiver 完成会话建立，而媒体流量先经过 Relay 再转发。Relay 是一个轻量级的 UDP 转发层，公共暴露面很小；Transceiver 是它背后的有状态 WebRTC 端点。Relay 不解密媒体、不运行 ICE 状态机、不参与编解码器协商——它只读取足够的包元数据来选择目的地，然后把包转发给拥有该会话的 Transceiver。从客户端的视角来看，WebRTC 会话没有任何变化。

The architecture we shipped splits packet routing from protocol termination. Signaling still reaches the transceiver for session setup, while media enters through the relay first. The relay is a lightweight UDP forwarding layer with a small public footprint, and the transceiver is the stateful WebRTC endpoint behind it.

The relay does not decrypt media, run ICE state machines, or participate in codec negotiation. It reads enough packet metadata to choose a destination, then forwards the packet to the transceiver that owns the session. The transceiver still sees a normal WebRTC flow and still owns all protocol state. From the client's perspective, nothing about the WebRTC session changes.

ICE ufrag：一个 WebRTC 里本来就有的路由钩子

首包路由是这个架构的关键步骤——Relay 必须在还没有任何会话存在时就能路由第一个包。每个 WebRTC 会话本身就携带一个协议原生的路由钩子：ICE 用户名片段（ufrag）。OpenAI 在生成服务端 ufrag 时嵌入了刚好足够的路由元数据，让 Relay 能推断出目标集群和拥有该会话的 Transceiver。信令阶段，Transceiver 分配会话状态并在 SDP 应答中返回共享的 Relay VIP 和 UDP 端口。客户端发出的第一个媒体路径包通常是一个 STUN 绑定请求。Relay 只需解析这个 STUN 包中的 ufrag，解码路由提示，就能把包转发到正确的 Transceiver。之后的 DTLS、RTP、RTCP 包都在已建立的会话内流动，不需要再解码 ufrag。

First-packet routing is the key step in this setup. A relay has to route the first packet from a client before any session exists on the packet path itself rather than by pausing on an external lookup service.

Every WebRTC session already carries a protocol-native routing hook: the ICE username fragment, or ufrag, a short identifier exchanged during session setup and echoed in STUN connectivity checks. We generate the server-side ufrag so it contains just enough routing metadata for relay to infer the destination cluster and owning transceiver.

During signaling, the transceiver allocates session state and returns a shared relay VIP and UDP port in the SDP answer. A VIP is a virtual IP address fronting the relay fleet; combined with the port, it gives the client a single stable destination, such as 203.0.113.10:3478, even though many relay instances sit behind it. The client's first media-path packet is usually a STUN binding request, which ICE uses to verify that packets can reach the advertised address.

Relay parses just enough of that first STUN packet to read the server ufrag, decode the routing hint, and forward the packet to the owning transceiver. Each transceiver listens on a shared UDP socket, meaning one operating system endpoint bound to an internal IP:port, not one socket per session. After the relay creates a session from the client's source IP:port to that transceiver destination, subsequent DTLS, RTP, and RTCP packets flow within the session without re-decoding the ufrag.

最好的复杂度藏在薄薄的路由层里，而不是每个后端服务中

缩小公共 UDP 暴露面后，OpenAI 将同样的 Relay 模式部署到了全球。Global Relay 是一组地理分布的中继入口点，用户的包在离自己最近的 Relay 进入 OpenAI 网络，而不是穿越公网到远端区域。这意味着更低的延迟、更少的抖动、更少的丢包。配合 Cloudflare 的地理引导信令，初始 HTTP/WebSocket 请求也会到达最近的 Transceiver 集群。这套架构的核心教训是：保持客户端的标准 WebRTC 行为不变、把硬状态集中在一个地方、利用协议中已有的信息做路由、在需要内核旁路之前先把简单的 Go 实现优化到位。实时语音 AI 只有在基础设施让延迟「隐形」时才真正可用。

Once we reduced the public UDP surface to a small number of stable addresses and ports, we could deploy the same relay pattern globally. Global Relay is our fleet of geographically distributed relay ingress points that all implement the same packet-forwarding behavior.

Broad geographic ingress shortens the first client-to-OpenAI hop because a packet can enter our network at a relay close to the user, in both geography and network topology, instead of crossing the public internet to a distant region first.

We use Cloudflare geo and proximity steering for signaling so the initial HTTP or WebSocket request reaches a nearby transceiver cluster.

The broader lesson is that the best place to add complexity is in a thin routing layer, not in every backend service, and not in custom client behavior. Encoding routing metadata into a protocol-native field gave us deterministic first-packet routing, a small public UDP footprint, and enough flexibility to place ingress close to users around the world.

端口耗尽和状态粘性：Kubernetes 上 WebRTC 的双重陷阱

第一个问题是端口模型本身。在高并发下，「每会话一个端口」意味着要暴露和管理巨大的 UDP 端口范围。云负载均衡器和 K8s service 不是为每个服务维护上万个公共 UDP 端口而设计的——每增加一段端口范围，就在负载均衡配置、健康检查、防火墙策略和发布安全上叠加一层运维复杂度。大量 UDP 端口还扩大了外部可达的攻击面，让网络策略审计更加困难。而且 K8s 中 Pod 不断被增删和重新调度，要求每个 Pod 预留大段稳定端口范围会破坏弹性伸缩。第二个问题更棘手：即使用「每服务器一个端口」解决了端口数量，还需要保证每个会话的包始终路由到拥有该会话的进程。因为 ICE 和 DTLS 是有状态协议——创建会话的进程必须持续接收该会话的包，才能验证连接检查、完成 DTLS 握手、解密 SRTP。如果同一会话的包落到了不同进程上，建连会失败或媒体会中断。

The first problem was the one-port-per-session model itself. At high concurrency, that means exposing and managing very large UDP port ranges.

Cloud load balancers and Kubernetes services are not designed around tens of thousands of public UDP ports per service. Each additional range adds operational complexity in load balancer config, health checking, firewall policy, and rollout safety.

Single-port-per-server designs solve port count, but they introduce a second problem: preserving ownership of each session across a fleet.

ICE and DTLS are stateful protocols. The process that created a session needs to keep receiving that session's packets so it can validate connectivity checks, complete the DTLS handshake, decrypt SRTP, and process later session changes such as ICE restarts. 用 Go 写一个足够窄的转发器，简单到不需要内核旁路

Relay 服务用 Go 编写，设计上刻意保持狭窄。在 Linux 上，内核网络栈从网卡接收 UDP 包并投递到 socket——Relay 作为用户态进程从该 socket 读取包头、更新少量流状态、然后转发包，全程不终结 WebRTC。三个关键设计选择：不做协议终结（只解析 STUN 头和 ufrag，后续 DTLS/RTP/RTCP 包保持不透明）、临时状态（维护一个小型、短超时的内存映射）、水平可扩展（多个实例并行运行在负载均衡器后面，重启只造成短暂流量中断）。性能优化方面：SO_REUSEPORT 让同一机器上的多个 worker 绑定同一个 UDP 端口，内核自动分发包避免单读循环瓶颈；runtime.LockOSThread 把每个 UDP 读取的 goroutine 固定到特定 OS 线程，配合 SO_REUSEPORT 让同一流的包倾向于落在同一 CPU 核上，改善缓存局部性；预分配缓冲区和最小化拷贝降低解析开销，避免 Go 的垃圾回收。

We wrote the relay service in Go and kept the implementation narrow on purpose. On Linux, the kernel's networking stack receives UDP packets from the machine's network interface and delivers them to a socket, the operating system endpoint that a process reads after binding an IP:Port. Relay runs in userspace, so a regular Go process reads packet headers from that socket, updates a small amount of flow state, and forwards packets without terminating WebRTC. We did not need any kernel-bypass framework.

No protocol termination: Relay parses only STUN headers/ufrag; it uses cached state for subsequent DTLS, RTP, and RTCP, keeping packets opaque.

Ephemeral state: It maintains a small, short-timeout, in-memory map of client address to transceiver destination for flow state and observability.

Horizontal scalability: Multiple relay instances run in parallel behind a load balancer. State is not hard WebRTC state, so restarts cause minimal traffic drops and quick flow recovery.

SO_REUSEPORT is a Linux socket option that allows multiple relay workers on the same machine to bind the same UDP port. The kernel then distributes incoming packets across those workers, which avoids a single read-loop bottleneck.

runtime.LockOSThread pins each UDP-reading goroutine to a specific OS thread. Combined with SO_REUSEPORT, that tends to keep packets from the same flow on the same CPU core, improving cache locality and reducing context switching.

Pre-allocated buffers and minimal copying keep parsing and allocation overhead low to avoid garbage collection in Go.
