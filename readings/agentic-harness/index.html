ACT I — 问题

Harness 决定
Agent 上限

Coding Agent 在长周期软件工程任务上取得了可衡量的进展——但这种进展不仅依赖于底层语言模型，同样依赖于模型周围的工程组件：塑造工作风格的系统 prompt、暴露文件系统和 shell 的工具、控制上下文和执行的中间件、以及恢复机制。这些模型外部的可编辑组件，被统称为 agent 的harness。研究表明，即使基础模型不变，harness 设计也能显著改变任务完成率。这意味着 harness 工程是提升 coding agent 的一等公民杠杆——针对一个模型优化的 harness 用在另一个模型上可能表现更差，必须随模型变化而重新适配。

原文

Coding agents are increasingly deployed on long-horizon software-engineering tasks, with measurable progress on issue resolution over real-world code repositories and multi-step terminal workflows. In practice, such progress relies not only on the underlying language model, but equally on the surrounding engineering components: the system prompt that shapes work style, the tools that expose the file system and shell, and the middleware that controls context, execution, and recovery. This collection of model-external, editable components is collectively referred to as the agent's harness.

Harness design materially shifts task completion on long-horizon coding benchmarks, even with the base model held fixed, making harness engineering a first-class lever for improving coding agents. Moreover, the optimal harness is model-specific: a harness tuned for one base model often underperforms on another and must be re-adapted as the base model changes.

ACT I — 瓶颈

手动调 Harness
跟不上了

在当前实践中，harness 适配是手动完成的——开发者检查运行轨迹、识别反复出现的失败模式、手工修改 prompt/tools/middleware/skills。但随着基础模型快速推进，模型能力和 harness 跟进之间的差距越来越大。一个直觉的方向是用进化 agent 来自动优化 harness，但现有方法面临两个结构性障碍：第一，长且无结构的轨迹产生的可操作信号很少；第二，紧耦合的 harness 框架使得超出 prompt 之外的编辑容易出错。这留下了一个核心问题：进化 agent 如何能联合且稳定地进化 harness 的所有可编辑组件？

原文

In current practice, this adaptation is performed manually—developers inspect trajectories, identify recurring failure patterns, and hand-craft edits across prompts, tools, middleware, and skills. Yet as base models advance rapidly, this manual loop struggles to keep pace, creating a widening gap between model capability and the harness needed to realize it.

An intuitive direction is to automate this loop with an evolution agent that optimizes harness components based on experience. However, few existing approaches jointly evolve the full set of editable components; most focus on a single component, typically the prompt, skills, or an in-context playbook. Jointly evolving multiple components end-to-end faces two structural obstacles: long, unstructured trajectories yield little actionable signal, and tightly coupled harness frameworks make edits beyond the prompt error-prone.

This leaves the central question of agent-driven harness evolution open: How can an evolution agent jointly and stably evolve all editable components of a coding agent's harness?

ACT II — 方法

三支柱：
可观测性驱动进化

论文的核心洞察是：瓶颈不在 agent 能力，而在可观测性。一旦进化 agent 获得了结构化的上下文和清晰的行动空间，它就能可靠地收敛到更好的 harness 设计。他们提出了 Agentic Harness Engineering（AHE），一个由三个可观测性支柱驱动的闭环：组件可观测性通过解耦的 harness 底座让每个 failure pattern 映射到单个组件文件；经验可观测性从数百万 token 的原始轨迹蒸馏出分层证据语料库；决策可观测性让每次编辑附带自声明预测，下一轮验证。三根支柱将每次编辑变成可证伪的合约。

原文

Our central insight is that this question is bottlenecked by observability, not by agent capability: once the evolution agent receives structured context over a clear action space, it can reliably converge on better harness designs. We implement this in Agentic Harness Engineering (AHE), a closed loop driven by three observability pillars: component observability via a decoupled harness that exposes seven editable component types as files, so each failure pattern maps cleanly to a single component class; experience observability via a layered, drill-down evidence corpus distilled from millions of raw trajectory tokens, so the evolver consumes structured root causes rather than raw logs; and decision observability via a change manifest that pairs every edit with a self-declared prediction, later verified against the next round's task-level outcomes, so each edit becomes a falsifiable contract and ineffective ones are reverted at file granularity.

ACT II — 底座

组件可观测：
解耦的 NexAU

AHE 的 harness 基于 NexAU 框架，将七种正交的组件类型暴露为工作区中的独立文件：system prompt、tool description、tool implementation、middleware、skill、sub-agent configuration、long-term memory。这些组件类型是松耦合的——添加一个 middleware 不需要修改 system prompt，添加一个 skill 不需要动任何 tool。这种解耦实现了组件可观测性：每个 failure pattern 映射到一个组件类，进化 agent 的每次 pass-rate 变化都定位到单个文件而非散布在数百行 prompt 中。种子 harness 刻意设计为极简——只有一个 shell 执行工具，没有 middleware、没有 skill、没有 sub-agent——让 AHE 添加的每个组件都必须从实测中赚取它的位置。

原文

We instantiate the harness on the NexAU framework, which exposes seven orthogonal component types as explicit files at fixed mount points in a single workspace: system prompt, tool description, tool implementation, middleware, skill, sub-agent configuration, and long-term memory. The component types are loosely coupled, so adding a middleware does not require editing the system prompt, and adding a skill does not require touching any tool.

This decoupling is what realizes component observability: each failure pattern maps to a single component class, giving the evolve agent a clean action space and localizing every pass-rate change to one file rather than scattering it across hundreds of lines of unstructured prompt prose.

Our seed harness is deliberately minimal: a single shell-execution tool, no middleware, no skills, no sub-agents. A seed already fitted to the target benchmark would contaminate every subsequent edit's attribution, since we could not tell whether a gain came from the loop or from the seed.

ACT II — 蒸馏

经验可观测：
Agent Debugger

每轮迭代中，AHE 为基准测试中的每个任务生成 k 条轨迹，这些轨迹可能包含错误——但它们散布在数百万 token 的原始消息中。为了提取可操作的洞察，他们使用 Agent Debugger 框架：将轨迹重构为可导航的、基于文件的环境，每条轨迹消息是独立文件，通过 shell 和脚本工具探索。Debugger 分析每个任务的失败根因或成功模式，产出per-task 分析报告。然后所有报告被聚合成一份benchmark-level 概览，作为进化 agent 每轮的入口。这实现了经验可观测性——从约 1000 万 token 蒸馏到约 1 万 token 的结构化证据。

We generate k traces for each task in a benchmark using a harness, which may contain errors resulting from the deficiencies of the harness that can be acted on, but scattered across millions of tokens of raw messages. ACT II — 合约

决策可观测：
可证伪的合约

Evolve Agent 在每轮中读取证据语料库，决定添加、修改或删除哪些 harness 组件，并记录每次编辑的理由。两个约束确保决策可观测性：第一，可控性——Evolve Agent 只能在 harness 工作区内写入，runs 目录、tracer、verifier 和 LLM 配置都是只读的，种子 system prompt 标记为不可删除。第二，每个变更都是证据驱动的——每次编辑附带一个 manifest 条目，记录失败证据、推断的根因、目标修复，以及预期影响（预期修复哪些任务 + 预计导致哪些回归）。下一轮中，这些预测与实际的 task-level 变化交叉比对——每次编辑因此变成了一个可证伪的合约，无效编辑在文件粒度被回滚。

原文

The Evolve Agent closes the AHE loop. In each round it reads the layered evidence corpus produced by the Agent Debugger, decides which harness components to add, modify, or remove, applies those edits to the workspace, and records the reasoning behind every edit. Two constraints govern these edits, and together they realize decision observability.

The first constraint is controllability: the Evolve Agent writes only inside the harness workspace, while the runs directory, tracer, verifier, and LLM configuration are read-only, and the seed system prompt is marked non-deletable.

The second constraint is that every change is evidence-driven and ships with a recorded prediction. Each edit attaches a manifest entry that names the failure evidence, the inferred root cause, the targeted fix, and a predicted impact comprising both expected fixes and at-risk regressions. In the next round, the loop intersects the predicted-fix and predicted-regression sets with the observed task-level deltas to produce a per-edit verdict. Each edit thereby becomes falsifiable by the next evaluation, which replaces rationale-driven self-justification with a measurable contract between rounds.

ACT III — 结果

69.7% → 77.0%
超越人类设计

在 Terminal-Bench 2 的 89 个任务上，AHE 从只有 bash 工具的极简种子 NexAU₀（69.7%）出发，经过 10 轮自动进化达到 77.0% pass@1。这超过了三个人类设计的 harness：opencode（47.2%）、terminus-2（62.9%）、Codex-CLI（71.9%），也超过了两个自进化基线 ACE（68.9%）和 TF-GRPO（72.3%）。按难度看，AHE 在 Easy 和 Medium 上达到 100.0% 和 88.2%。而其他纯 prompt 自进化方法（ACE/TF-GRPO）之所以落后，是因为它们只编辑 prompt，从未触及 tools、middleware 和 long-term memory——恰恰是 AHE 增益最大的组件。

ACT IV — 迁移与局限

冻结迁移
与回归盲区

AHE 的 harness 在 GPT-5.4 high 上针对 Terminal-Bench 2 进化。但冻结的 harness 直接迁移到了 SWE-bench-verified（500 个任务、7 个仓库），不做任何 re-evolution，aggregate 成功率达到 75.6%，同时比 NexAU₀ 种子少用 12% 的 token。跨模型迁移到 5 个不同的基础模型也全部获得正增益（+2.3 到 +10.1 pp），离 saturation 越远的模型增益越大——说明 AHE 编码的是通用的工程协调模式，而非 benchmark 特定的窍门。不过论文也坦诚指出一个关键弱点：AHE 的回归预测精度只有 11.8%（仅比随机高 2 倍），意味着大部分即将发生的回归无法被预见——这是未来自进化循环最需要改进的方向。

Without further evolution, the frozen harness transfers to SWE-bench-verified it tops aggregate success at 12% fewer tokens than the seed, and on Terminal-Bench 2 it yields +5.1 to +10.1 pp cross-family gains across three alternate model families, indicating the evolved components encode general engineering experience rather than benchmark-specific tuning.

Cross-family gains dominate within-family ones: deepseek-v4-flash moves +10.1 pp from 51.7% to 61.8%, qwen-3.6-plus +6.3 pp from 56.2% to 62.5%, and gemini-3.1-flash-lite-preview +5.1 pp from 36.5% to 41.6%.

Regression blindness. The regression panel tells the opposite story: cross-iteration regression-precision of 11.8% and regression-recall of 11.1% sit only about 2x above their random baselines of 5.6% and 5.4%, so most upcoming regressions go unforeseen. The agent can justify why an edit should help, but it cannot reliably name the tasks the same edit is about to break, which is what produces the non-monotone steps in the evolution curve.

进化曲线：
10 轮关键编辑

10 轮进化并非单调上升——每轮都可能引入回归。但从整体趋势看，best-so-far 从 69.7% 一路攀升到 77.0%。论文标注了 4 个里程碑编辑：第 2 轮的「contract-first workflow + 可调 shell timeout」（prompt + tool）从种子起跳；第 4 轮的「publish-state guard」（prompt + tool）保护验证后的状态不被破坏；第 5 轮的「cross-step risk monitor」（middleware）通过观察命令序列发现潜在风险；第 7 轮的「post-success hard-block + pre-turn risk salience」（tool + middleware）阻止成功后的意外覆写。每次增益都精确归因到具体的组件文件。

Table 3 decomposes the AHE gain at the component level. Each "+ X only" row takes the NexAU₀ seed and swaps in one component from the fully evolved AHE configuration, namely long-term memory, tools, middleware, or system prompt, leaving the other three at their seed defaults. Each component owns a different failure surface. Memory adds 12 boundary-case lessons; on Hard the lessons lift it above full AHE, while on Easy they reduce to superfluous re-verification. Tools become a 1364-line shell that auto-surfaces contract hints from files near each command. Middleware adds a finish-hook that forces one evaluator-isomorphic closure check.

Components interact non-additively, capping the aggregate gain. The three positive single-component gains sum to +11.1 pp against full AHE's +7.3 pp, and on Hard the memory-only variant exceeds full AHE: memory, middleware, and the system prompt all push toward the same closure-style verification, so stacking them spends turns on redundant re-checks within the long-horizon budget.
