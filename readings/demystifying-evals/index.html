没有 Eval 的团队，永远在救火

一个没有 eval 的团队是什么状态？用户投诉了才知道出了问题，修了一个 bug 又引出三个新 bug，上线新功能不知道会不会把旧功能搞坏。Anthropic 把这叫做「救火循环」——团队被困在一个永远在灭火、永远不知道下一把火在哪里的死循环里。Eval（评测）就是打破这个循环的方法：它让你在代码推送之前就能看到问题，让你用数据而不是直觉来判断「到底变好了还是变差了」。Claude Code 的开发历程就是一个典型例子——从靠手动测试和用户反馈起步，逐步加入针对简洁性、文件操作、不必要复杂度等维度的评测，最终实现了在规模化开发中持续改进。

Introduction

Effective evaluations enable teams to deploy AI agents with greater confidence. Without them, organizations become trapped in reactive cycles—discovering issues only after production deployment, where one fix frequently cascades into additional problems. Evaluations make performance issues and behavioral shifts apparent before impacting end users, and their value multiplies throughout an agent's lifecycle.

ACT I · 基础概念

Eval 的六块积木

一次 eval 就像一场考试，由六个基本组件构成。Task（题目）——一道有明确输入和判定标准的题目。Trial（作答）——每次执行就是一次作答，因为 LLM 有随机性，所以同一题要考多次才有统计意义。Grader（阅卷官）——判定答案好不好的逻辑，一道题可以有多个 Grader 从不同维度评分。Transcript（答卷）——完整的作答记录，包括工具调用、推理过程和中间结果。Outcome（最终状态）——考完后环境的实际变化，区分「Agent 说它做了什么」和「它实际改变了什么」。Harness（考场）——管理整个考试流程的基础设施。理解这六个概念，是设计好 eval 的前提。

Essential Definitions

Task (problem/test case): A single examination with specified inputs and success conditions. Trial: Each execution attempt; multiple trials run due to model output variability. Grader: Logic assessing agent performance dimensions; tasks contain multiple graders with various assertions. Transcript (trace/trajectory): Complete trial record—outputs, tool usage, reasoning, intermediate findings, interactions. Outcome: Final environmental state after trial completion; distinguishes stated results from actual system changes. Evaluation harness: Infrastructure managing end-to-end evaluation.

ACT II · 评分方法

三种裁判，各有所长

Eval 有三种判分方式，各有优劣。Code-based Grader（代码评分）是最快最便宜的——字符串匹配、单元测试、静态分析，结果确定且可复现，但对开放式任务无能为力。Model-based Grader（模型评分）用 LLM 来打分——可以评价文风、逻辑性、是否有同理心，灵活且能处理主观任务，但结果不确定、成本更高、需要和人类校准。Human Grader（人工评分）是最高质量的判断——专家评审、众包评测，但贵、慢、难以规模化。实践中通常组合使用：先用代码评分做基础判定，再用模型评分补充主观维度，定期用人工评分来校准模型评分的标准。

Types of Graders

Code-Based Graders: String matching, binary success/failure tests, code analysis, outcome verification. Strengths: Speed, cost-effectiveness, objectivity, reproducibility. Weaknesses: Sensitivity to acceptable variations, limited sophistication. Model-Based Graders: Criteria-based scoring, linguistic assertions, comparative evaluation. Strengths: Flexibility, scalability, nuance capture. Weaknesses: Non-deterministic results, expense, human calibration requirements. Human Graders: Expert evaluation, crowdsourced assessment. Strengths: Highest-quality judgments. Weaknesses: Expense, duration, specialist access requirements.

ACT III · 分类评测

四类 Agent，四种考法

不同类型的 Agent 需要截然不同的评测策略。Coding Agent 最幸运——代码能不能跑、测试过不过，天然适合确定性评分，SWE-bench 一年内把前沿模型从 40% 推到了 80% 以上。Conversational Agent 最有挑战——不仅要判断工单有没有关闭，还要评价交互质量：有没有共情？有没有在 10 轮内解决？Research Agent 最主观——「全面、有据、准确」在市场分析和学术报告中标准完全不同。Computer Use Agent 最接近人——用截图和点击操作软件，需要真实或隔离环境来验证任务是否真的完成了。

ACT III · 统计学

同一道题，十次八个答案

AI Agent 每次运行结果都不一样——同一道题可能跑 10 次对 7 次。怎么衡量这种不确定性？两个核心指标。pass@k——k 次尝试中至少成功一次的概率。k 越大概率越高，适合「只要有一次能跑通就行」的场景，比如生成多个方案选最好的。pass^k——k 次全部成功的概率。k 越大概率越低，适合需要一致可靠性的客户场景。比如单次成功率 75%：三次中至少成功一次的概率高达 98%，但三次全成功只有 42%。选哪个指标，取决于你的场景需要「一次成功」还是「次次可靠」。

Non-Determinism

pass@k: Probability that agents generate minimum one correct solution within k attempts. Increasing k elevates pass@k. 50% pass@1 indicates half the tasks succeed initially. pass^k: Probability that all k trials succeed. Increasing k reduces pass^k since consistency across more attempts demands higher standards. With 75% per-trial success across three trials: (0.75)^3 ≈ 42%.

ACT IV · 避坑

聪明反被聪明误：Eval 的经典陷阱

评测设计中有很多经典坑。评分太严格——Opus 4.5 在 CORE-Bench 上最初只得了 42%，后来研究者发现是评分逻辑有问题：把「96.12」判为不等于「96.124991…」。修正评分方式和放宽框架约束后，成绩飙升到 95%。规格不明确——Terminal-Bench 有些题没指定文件路径，但阅卷时假设了特定路径，Agent 明明做对了却被判错。单向评测——Claude.ai 的搜索评测发现，如果只测「应该搜索」的场景，Agent 就倾向于什么都搜索，所以必须同时测「不该搜索」的情况才能得到平衡的行为。还有一个容易被忽视的陷阱：饱和——当评测分数接近 100% 时，它就从改进工具变成了回归检测工具。

Step 5 + Step 7

Opus 4.5 initially scored 42% on CORE-Bench until researchers discovered multiple problems: rigid grading penalizing "96.12" vs. "96.124991…", ambiguous specifications, stochastic tasks resisting exact reproduction. After corrections and less-constrained frameworks, performance reached 95%. Terminal-Bench investigations revealed tasks requesting script composition without filepath specification, yet grading presumed particular locations, causing agent failure despite competent execution. Claude.ai's search evaluation required preventing inappropriate searches while preserving research capability—requiring dual evaluation: circumstances warranting search and relying on knowledge.

ACT V · 全局

瑞士奶酪：每层都有洞，叠起来才安全

Eval 不是唯一的质量保障——它是多层防线中的一层。就像安全工程中的「瑞士奶酪模型」：每一层防线都有漏洞，但多层叠加起来，一层漏掉的问题会被下一层拦住。文章列出了六种方法：自动 eval（开发阶段，每次提交都跑，快但可能脱离真实使用）、生产监控（上线后，真实规模但只能事后发现问题）、A/B 测试（严格对比但耗时长）、用户反馈（真实但稀疏且偏向严重问题）、人工审查 transcript（高质量但不可规模化）、系统性人工评估（最权威但最贵最慢）。最强的团队把这些方法组合使用：自动 eval 加速迭代，生产监控保持接地气，定期人工评审校准标准。

四类评测 · 确定性与主观性

Coding Agent：代码跑得过就是硬道理

Coding Agent 的评测天然适合确定性方法——代码能不能编译、测试过不过、静态分析有没有安全漏洞，这些都能用代码评分直接判定。SWE-bench Verified 的做法是：给 Agent 一个 GitHub issue，让它修复代码，然后跑测试——修好了 failing test 同时没搞坏其他 test 就算通过。除了结果判定，transcript 评分也很有价值：检查 Agent 有没有先读代码再改、有没有跑测试、代码风格如何。Research Agent 则完全不同——「全面」和「准确」是主观的。BrowseComp 测试的是 Agent 能否在海量网页中找到特定信息（容易验证但难以完成），而实际的研究评测需要组合多种 grader：groundedness check（引用是否支持结论）、coverage check（关键事实是否都涵盖）、source quality check（来源是否权威）。

Coding + Research Agents

SWE-bench Verified provides agents GitHub issues from prevalent Python repositories, grading via test suite execution; solutions succeed only when fixing failing tests without breaking existing ones. LLMs advanced from 40% to >80% on this benchmark within one year. Research evaluations confront particular obstacles: experts frequently disagree on synthesis comprehensiveness, ground truth shifts continuously alongside reference content updates, and extended open-ended outputs create error opportunities.

四类评测 · 交互与界面

对话 Agent 和 Computer Use：评的不只是结果

Conversational Agent 的特殊之处在于——交互质量本身就是评测对象。工单关了不够，还得问：Agent 有没有共情？有没有在合理轮数内解决？有没有正确调用工具？tau-Bench 的做法是用一个 LLM 模拟客户（比如愤怒的退货用户），另一个 LLM 作为 Agent 处理，然后从状态验证（工单是否 resolved）、transcript 约束（是否在 10 轮内完成）和 LLM rubric（沟通质量评分）三个维度综合判分。Computer Use Agent 面临独特挑战——它通过截图和点击操作软件，不走 API。WebArena 通过 URL 和页面状态验证导航任务，同时检查后端数据库确认操作真正执行了（比如订单确实下了，而不仅仅是显示了确认页面）。Claude for Chrome 的开发团队甚至用 eval 来决定具体实现方式——发现维基百科摘要用 DOM 文本提取更快，而亚马逊购物用截图更好。

路线图 · 收集与设计

Step 0-3：先有题，再有考场

Step 0: 尽早开始——不要等到有几百道题才开始，20-50 道从真实失败中提取的题就够了。早期改动效果明显，小样本就能看出差异。Step 1: 利用现有的手工验证——把你发版前手动检查的行为、用户常做的操作转化成测试用例。查 issue tracker 和客服记录，把用户报告的 bug 变成题目。Step 2: 写清楚规格——关键标准是：让一个独立的领域专家来做这道题，他能不能得出和你一样的判定？如果不能，说明规格还不够清楚。同时要做参考实现——已知能通过所有 grader 的标准答案。Step 3: 正反兼顾——如果只测「该搜索时搜索」，Agent 就会什么都搜索。必须同时测「不该做什么」，才能得到平衡的行为。

Steps 0-3

Teams frequently delay because hundreds of tasks seem necessary. Actually, 20-50 basic tasks drawn from genuine failures provide excellent foundations. Begin with current development verification—behaviors confirmed pre-release and common user tasks. Competent specifications ensure independent expert evaluation reaches identical verdicts. Evaluate both occurrence and non-occurrence scenarios. One-directional evaluation produces one-directional optimization.

路线图 · 基础设施与维护

Step 4-8：搭考场、看答卷、防饱和

Step 4: 干净环境——每次 trial 必须从零开始，不能有上次运行的残留。Anthropic 发现 Claude 会去读上一次运行的 git 记录，这会导致虚假的成功。Step 5: 聪明评分——能用确定性方法就用确定性方法，LLM 评分只在必要时补充。关键原则是「评结果不评过程」——不要要求 Agent 按特定步骤做事，因为前沿模型经常发现你没想到的合理路径。给部分分而不是全有全无。Step 6: 读 transcript——不读 transcript 就不知道分数是否可信。失败要看是真的做错了还是被误判了，成功要看是不是靠了不该靠的捷径。Step 7: 关注饱和——当分数接近 100%，eval 的作用从「推动改进」变成「防止退步」。Step 8: 持续维护——eval 需要有人负责，就像单元测试一样。离产品最近的人（PM、客服、销售）最懂什么是「成功」。

Steps 4-8

Each trial begins fresh. Leftover artifacts, stored data, resource exhaustion cause correlated failures from infrastructure rather than agent capability. Inflexible step-sequence grading often proves excessive, generating brittle tests when agents regularly discover unanticipated valid approaches. Rather than penalizing creativity, prioritize output grading over process grading. Score quality remains unknown without reading numerous trial transcripts. Anthropic invested in transcript visualization infrastructure and regularly reviews them. Reaching 100% converts improvement tracking into regression monitoring.
