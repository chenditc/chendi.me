Speculative Decoding

EAGLE 不是让大模型少想，而是让它一次验收更多答案。

你已经理解 transformer 的基础推理过程，所以可以把瓶颈看得很直接：LLM 每生成一个 token，都要用目标模型做一次前向计算。EAGLE 的目标不是改变目标模型，也不是降低精度，而是先用一个很轻的 draft model 猜出后面一小串候选，再让目标模型用一次并行验证吃掉多个 token。

EAGLE 原论文把问题起点描述为 autoregressive decoding 导致 LLM 生成慢且成本高；每个 token 顺序生成，所以延迟很难靠单次前向内部优化完全消除。资料：EAGLE paper。

Speculative decoding 的基本交换是：便宜地猜，昂贵地验。

普通 speculative decoding 先让小模型快速生成几个 draft tokens，然后目标 LLM 在一次 forward pass 中并行算出这些位置的概率。因为验证阶段按严格的接受/拒绝规则处理候选，所以只要实现符合算法，最终输出分布可以与直接用目标 LLM 采样保持一致。

EAGLE 论文的 preliminaries 说明 speculative sampling 分成 draft 与 verification 两阶段；验证阶段按概率接受候选，拒绝后重采样，因此等价于直接从目标模型采样。资料：EAGLE HTML。

EAGLE 的关键不是另找一个小 LLM，而是在 feature 空间里续写。

EAGLE 认为，token 序列是离散自然语言，直接预测下一个 token 容易受表面词形影响；而目标模型倒数第二层的 hidden feature 更接近连续语义状态，所以更容易被一个轻量 autoregression head 预测。EAGLE 再把“已经采样出来的下一步 token”也输入 draft model，用 shifted-token 消掉采样随机性带来的歧义。

EAGLE 原论文给出两点观察：feature-level autoregression 比 token-level 更直接；但 feature 预测会被采样随机性限制。EAGLE 通过输入提前一步的 token sequence 来缓解这种 uncertainty。资料：arXiv:2401.15077。

Draft tree 让 EAGLE 一次下注多条路；验证规则保证它不会偷偷改答案。

EAGLE 不只生成一条候选链，而是用 tree attention 生成一棵 draft tree。目标模型随后在树上并行验证每个节点：如果前面的节点被拒绝，后面的分支会被丢弃；如果一段路径连续通过，系统就能一次接受多个 token。这里的“lossless”不是 draft model 永远猜对，而是猜错时目标模型会把它纠正回来。

EAGLE 论文说明它使用 tree attention 构造树状 draft，并由目标模型在 verification 阶段计算树中 token 的概率；论文也强调输出分布保持不变。资料：EAGLE Section 3。

EAGLE-2 的改动很务实：别固定树形，把预算投给更可能被接受的分支。

原始 EAGLE 使用 static draft tree，默认某个位置的接受率主要由位置决定。EAGLE-2 发现接受率还强烈依赖上下文，而且 EAGLE 的 draft confidence 与实际接受率相关，所以它用 confidence 动态扩展树，把更多候选给高概率路径，把验证容量从“平均分配”变成“按机会分配”。

EAGLE-2 论文指出 static draft tree 隐含接受率只由位置决定的假设，但实验发现接受率也依赖上下文；它利用 draft model confidence 近似 acceptance rate，并报告 3.05x-4.26x speedup。资料：EAGLE-2 paper。

EAGLE-3 又转向直接 token 预测，并用多层 feature 融合补信息。

EAGLE-3 的论文说，单纯扩大 EAGLE 的训练数据收益有限，因为 feature prediction 本身形成了约束。于是 EAGLE-3 放弃原来的 feature prediction 路线，改成 direct token prediction，同时通过 training-time test 融合目标模型多层 feature，让 draft model 能从更多训练数据中受益。

EAGLE-3 摘要说明它放弃 feature prediction，改用 direct token prediction，并用 multi-layer feature fusion 与 training-time test；论文报告最高 6.5x speedup，并在 SGLang 中观察到 batch size 64 下吞吐提升。资料：EAGLE-3 paper。

副作用不是“模型变笨”，而是系统复杂度、内存、调参和收益波动变高。

在严格 speculative sampling 验证下，EAGLE 的目标是保持输出分布不变，所以主要副作用不应理解为质量下降。真正的代价在工程侧：你需要加载 draft model 或额外 head，需要为 draft tree 和并行验证留显存，需要调 `num_steps`、`topk`、draft token 数；当任务难、采样温度高、batch 很大或 MoE 验证成本异常时，加速比也可能缩水。

SGLang 文档说明 speculative 参数会影响范围、拒绝级联、内存和计算消耗，并专门给出 OOM 排查步骤；vLLM 文档也提醒实际收益取决于模型、流量、硬件和采样设置。资料：SGLang docs，vLLM docs。

第一步：目标模型仍然先跑，EAGLE 复用它留下的 feature。

EAGLE 不是凭空预测未来。目标 LLM 生成当前 token 时，已经算出了倒数第二层 hidden feature；EAGLE 的 draft model 复用这些 feature，再拼上提前一步的 token embedding。这样 draft model 看到的不是裸 token 历史，而是目标模型刚刚形成的内部语义状态。

EAGLE 论文定义 feature 为目标 LLM LM head 前的 hidden state，并说明 draft model 输入 feature sequence 与 shifted token sequence。资料：EAGLE Section 3.1。

第二步：shifted token 解决“我到底采样到了哪条路”的不确定性。

如果只给 feature，draft model 会遇到一个问题：同一个历史状态可能采样出不同 token，而不同 token 会把后续 feature 带到不同方向。EAGLE 把已经采样出来的 token 提前一格输入，所以 draft model 知道真实走的是哪条分支，而不是在多个可能世界之间平均。

EAGLE 论文用 feature uncertainty 解释采样结果会导致后续 feature 分叉，并指出 shifted-token 输入能处理这种随机性。资料：EAGLE paper。

第三步：接受不是全有全无，而是从前往后逐个核验。

目标模型验证 draft tree 时，会按 speculative sampling 的规则逐个接受候选 token。前两个 token 可能直接通过，第三个也可能通过，但一旦某个位置被拒绝，它之后依赖这条路径的 token 就不能继续用了。这个机制解释了为什么 acceptance length 是核心指标：它决定每次昂贵验证能换来多少真实 token。

接受长度 = 3，下一轮从 t4 的纠正结果继续。

EAGLE 论文实验部分把 average acceptance length 定义为目标 LLM 每次 forward 接受的平均 token 数，并用它衡量加速效果。资料：EAGLE experiments。

副作用一：低延迟不等于所有场景吞吐都暴涨。

Speculative decoding 最容易在 batch 小、中低 QPS、decode 受内存带宽限制的场景里体现 token 间延迟收益。可是当服务已经处在高并发、大 batch 或验证阶段成为主导时，draft 开销、树验证开销和调度开销会侵蚀收益，所以工程上必须用自己的请求分布 benchmark，而不能直接搬论文里的倍数。

vLLM 文档把 speculative decoding 描述为降低中低 QPS 与内存受限工作负载的 token 间延迟，并提醒实际收益取决于模型、流量、硬件和采样设置。资料：vLLM speculative decoding。

副作用二：draft tree 越贪心，越容易把显存和计算推上去。

`num_steps` 增大时，EAGLE 猜得更远，但错误后丢弃的后续 token 也更多；`topk` 增大时，树的分支更多，候选覆盖更好，但 draft 和 verification 都要处理更多节点；`num_draft_tokens` 增大时，目标模型一次能验证更多候选，但显存压力也随之增加。

num_steps ↑看得更远，也更可能出现拒绝级联。
topk ↑分支更多，接受机会和计算开销一起上升。
draft tokens ↑验证容量更大，但 GPU memory 占用更高。
阈值/量化/编译不同框架和硬件下需要实际测量。
paraphrased source

SGLang 文档解释 `speculative-num-steps`、`speculative-eagle-topk`、`speculative-num-draft-tokens` 分别影响推测范围、分支因子和并行验证容量，并明确提到内存/计算消耗。资料：SGLang speculative decoding。

副作用三：lossless 依赖“验证算法正确”，不是依赖“draft model 很聪明”。

如果你使用的是标准 speculative sampling 验证，EAGLE 可以把质量风险转移成性能风险：draft 猜错会少接受 token，而不是直接污染输出。但如果实现为了速度放松接受规则、改了采样分布、或者用了不匹配的非官方 checkpoint，那么“输出分布不变”这个结论就不能自动套用。
