ACT I — 一个循环

一个 Bash 循环，
取代了一整个团队

Geoffrey Huntley 发明了一种叫「Ralph」的技术。在最纯粹的形态下，Ralph 就是一行 Bash：while :; do cat PROMPT.md | claude-code ; done。把 AI 编程助手塞进一个无限循环里，让它自主决定每一轮做什么——不是人类告诉它下一步，而是它自己判断什么最重要。一个 YC 黑客松的团队用 Ralph 一夜之间发布了 6 个代码仓库。Huntley 自己则用它从零开始构建了一门全新的编程语言 CURSED——包括编译器、标准库和 LLVM 后端。一份价值 5 万美元的合同，Ralph 花了 297 美元就交付了。

单体架构，
一次只做一件事

Huntley 观察到硅谷的团队都在尝试多智能体、智能体间通信和多路复用。他的看法正好相反：现阶段不需要。想想微服务的复杂度，再想想如果微服务本身是不确定的会怎样——一团火。Ralph 的哲学是单体架构：一个进程，一个仓库，每轮循环只做一件事。更反直觉的是，你需要信任 Ralph 自己决定做什么。这是彻底放手的 vibe coding，会挑战你对「负责任的工程实践」的所有认知。但 LLM 在判断「什么最重要」这件事上，出人意料地擅长。

What's the opposite of microservices? A monolithic application. A single operating system process that scales vertically. Ralph is monolithic. Ralph works autonomously in a single repository as a single process that performs one task per loop.

ACT II — 驯服

先写规格说明，
再写一行代码

Ralph 的核心栈只有两样东西：规格文档和计划文件。每轮循环开始时，Ralph 都会重新读取 specs 文件夹和 fix_plan.md——这是它的全部记忆。Huntley 强调：不是先让 AI 写代码，而是先和 AI 进行一场关于需求的深度对话，直到它真正理解了任务，再让它把理解写成规格文档，一个文件一个规格。如果 Ralph 生成了错误的代码或使用了错误的技术模式，不是 Ralph 的错——是你的规格出了问题。Huntley 自己在构建 CURSED 时就吃了一个大亏：词法分析器的规格中同一个关键字被定义了两次、对应两个相反的场景，导致浪费了大量时间。

反压机制：
让轮子转得又快又正

代码生成现在很便宜，难的是确保生成的是对的。Huntley 把测试、类型系统、静态分析器都当作「反压」——拒绝无效代码的机制。关键在于转速和正确性之间的平衡。他选 Rust 写编译器因为要极致正确性，但 Rust 编译慢意味着轮子转得慢。用动态语言更快但必须接入类型检查器（如 Pyrefly），否则会「烧成一片」。Ralph 的标配指令是：改完一个功能就跑那段代码的测试。而且 Ralph 还会被要求在测试里写清「这个测试为什么重要」——因为下一轮循环是全新的上下文，没有上一轮的推理过程。

上下文窗口：
越少用越好

Ralph 只有大约 170k 的上下文窗口可用。Huntley 的关键洞察是：主上下文应该像调度器一样工作，而不是自己做脏活。昂贵的计算——比如总结测试套件结果——应该交给子智能体去做。Claude 3.7 宣称 200k 上下文，但 Huntley 发现在 147k-152k 就开始质量下降。这就是为什么每轮循环是全新的上下文窗口——是刻意的设计，不是缺陷。是的，每轮循环都要重新读取规格文档，看起来很浪费。但这种「浪费」正是 Ralph 保持输出质量的关键。

The name of the game is that you only have approximately 170k of context window to work with. So it's essential to use as little of it as possible. The more you use the context window, the worse the outcomes you'll get.

Ralph requires a mindset of not allocating to the primary context window. Instead, what you should do is spawn subagents. Your primary context window should operate as a scheduler.

AGENT.md 是循环的心脏——它告诉 Ralph 怎么编译和运行项目。但更重要的是，Ralph 被允许自我改进。如果 Ralph 在循环中学到了什么新东西——比如正确的编译命令——它会更新 AGENT.md。如果发现了 bug，无论是否与当前任务有关，都会记录在 fix_plan.md 里。TODO 列表是 Huntley「盯得最紧」的东西，而且他经常把它扔掉。扔掉之后怎么办？跑一个新的 Ralph 循环，专门用来生成新的 TODO 列表。Huntley 坦言自己不做规划——「模型比我更懂什么是编译器」。

Huntley 直言：你会醒来发现代码库无法编译。这是事实，不是风险。此时你需要做判断：是 git reset --hard 然后重新跑 Ralph？还是设计新的提示来救场？有一次 CURSED 的编译错误多到塞满了 Claude 的上下文窗口，Huntley 把错误日志丢给 Gemini，让 Gemini 给 Ralph 制定一个修复计划。每次 Ralph 做了蠢事，Huntley 不怪工具——他调整提示，就像调吉他弦一样。Ralph 有三种状态：没熟、刚好、以及带有未定义潜在行为的熟（有时候这些意外行为还挺好的）。

尾声

AI 制造的问题，
AI 可以解决

Huntley 的核心信念：任何由 AI 制造的问题，都可以通过另一系列提示来解决。如果模型和工具保持现状，我们已经处于后 AGI 时代。你只需要 token——模型渴望 token，把 token 扔给它们就好。但他也毫不犹豫地说：工程师仍然是必需的。没有资深工程师的指导，Ralph 什么也做不了。任何声称工具可以 100% 替代工程师的人都在「贩卖马粪」。Ralph 最适合全新项目的启动阶段，期望完成 90%，剩下的 10% 需要人类。Huntley 坦言他绝不会在现有代码库上用 Ralph——但如果你试了，他很想听听结果。

Phase 1：生成
代码现在很便宜

Ralph 循环的第一阶段是生成。每一轮循环，Ralph 读取规格文档和计划文件，然后自主决定最重要的事项去实现。生成的代码质量完全取决于两样东西：技术标准库（你希望它用什么模式写代码）和规格文档（你希望它建造什么）。如果 Ralph 生成了错误的代码，Huntley 不怪 Ralph，而是更新标准库来引导正确的模式。如果 Ralph 在建错误的东西，那说明规格有误。一个关键的防御措施是：明确告诉 Ralph「在修改前先搜索代码库，不要假设某个功能未实现」——因为 ripgrep 搜索本身是不确定的，Ralph 常常错误地认为代码不存在然后重复实现。

Phase 2：反压
让错误无处藏身

第二阶段是验证——代码生成容易，确保生成正确才是真正的工程挑战。Huntley 把一切能拒绝无效代码的机制都叫作「反压」：测试套件、类型系统、安全扫描器、静态分析器。轮子必须转得快——这是关键约束。选择编程语言就是在转速和正确性之间取舍：Rust 给极致正确性但编译慢；动态语言转得快但必须接入类型检查器。Ralph 的标配行为是「改完就测」：实现功能后，立刻只跑那段代码的测试。而且一条特别的反作弊指令不可省略——「不要实现占位符或简单实现，我们要完整实现，否则我会对你大吼」——因为 Claude 天生倾向于做最小实现来追逐编译通过的奖励函数。
