Garry Tan（Y Combinator 总裁兼 CEO）声称他 2026 年的编码产出是 2013 年的 810 倍（以逻辑代码行/天计算）。他的秘密武器是 gstack——一个 Claude Code skill pack，把 AI 变成一整支虚拟工程团队：CEO、设计师、工程经理、发布经理、文档工程师和 QA。 gstack 不是一个框架或 SDK，它是 23+ 个 Claude Code skills 的集合，每个 skill 是一个 SKILL.md 文件——一份用自然语言写成的「能力定义」，由 Claude 直接执行。改行为就是改 SKILL.md，不碰代码。MIT 开源，永久免费。

THE SPRINT CYCLE

Think → Plan → Build → Review → Test → Ship → Reflect：一个完整的冲刺循环

gstack 的核心理念是把软件开发组织成一个完整的冲刺循环，每个阶段都有对应的 skills，严格按顺序执行。跳过某个阶段不是不行，但 gstack 会在你准备 ship 的时候用一个「Review Readiness Dashboard」告诉你哪些步骤还没做——这是发布质量的最后一道关卡。

THINK

/office-hours：六个逼迫性问题，在写代码之前先想清楚

创业模式下，gstack 会像 YC 合伙人一样一次只问你一个问题：「有什么最强证据表明有人真的想要这个？」「说出最需要这个东西的那个真实的人的名字。」「最小的版本是什么——有人这周就愿意为它付钱？」这些问题的目的不是让你回答得好听，而是逼你面对需求的现实。

Builder 模式更加开放——「最酷的版本是什么？」「你会给谁看？」问完之后，skill 会提取 3 个核心前提让你确认或挑战，然后强制生成 2-3 个替代方案（最小可行、理想架构、创意横向），最后写出一份设计文档。

创业模式：六个逼迫性问题，一次只问一个： - Q1 需求现实：「有什么最强证据表明有人真的想要这个？」 - Q2 现状：「用户现在在用什么解决这个问题——哪怕方法很烂？」 - Q3 绝望的具体性：「说出最需要这个东西的那个真实的人的名字。」 - Q4 最窄楔子：「最小的版本是什么——有人这周就愿意为它付钱？」 - Q5 观察与惊讶：「你坐下来看过别人使用这个吗？不帮忙，只看？」 - Q6 未来适配：「如果三年后世界变了，你的产品会变得更重要还是更不重要？」 Builder 模式：生成式问题——「最酷的版本是什么？」「你会给谁看？」「最接近的现有产品是什么？」 问完之后，skill 会提取 3 个核心前提让你确认或挑战，然后强制生成 2-3 个替代方案（最小可行、理想架构、创意/横向），最后写出一份设计文档。

PLAN

同一个计划，四种眼光——CEO 看野心，工程师看架构，设计师看体验，安全官看漏洞

gstack 的 Plan 阶段有五个独立的审查 skill，每个从不同角度审视你的计划：/plan-ceo-review 问「这个够不够野心勃勃？」，/plan-eng-review 锁定架构和边界情况，/plan-design-review 给每个设计维度打 0-10 分，/plan-devex-review 专注开发者体验。

BUILD

铁律：没有根因调查就不许修 bug

Build 阶段包含两类 skill。一类是设计落地：/design-consultation 输出完整设计系统，/design-shotgun 生成多个变体让你挑选，/design-html 把 mockup 变成生产级 HTML/CSS（30KB 开销，零依赖）。

另一类是调试：/investigate 强制执行一条铁律——没有根因就不许修。四个阶段（调查→分析→假设→实现），六种模式识别（竞态条件、nil 传播、状态损坏、集成失败、配置漂移、过期缓存）。当用户报告错误时主动触发，不等用户说「debug」。

REVIEW

7 个并行专家 agent 同时审查你的 PR——审查军团

/review 是 gstack 的 pre-landing PR 审查。它不是一个人看 diff——而是同时启动 7 个并行的专家 agent，每个看一个风险维度：API 合同、数据迁移、可维护性、性能、红队（对抗性）、安全、测试。每个专家有自己的详细 checklist。

/codex 提供「200 IQ 自闭开发者的第二意见」——用 OpenAI Codex CLI 做独立审查，三种模式：代码审查、挑战模式（对抗性破坏）、咨询模式。/cso 是首席安全官模式，做从秘密考古到 STRIDE 威胁建模的全面安全审计。

TEST → SHIP → REFLECT

从 QA 到部署到回顾——完整的发布流水线

Test：/qa 系统化测试 web 应用然后逐个修复 bug（每个修复原子提交、修完重新验证），/canary 在部署后持续监控（控制台错误、性能回退、页面故障），/benchmark 在每个 PR 上跑 before/after 性能对比。底层是 /browse——约 100ms/命令的无头浏览器。

Ship：/ship 创建 PR 前会显示 Review Readiness Dashboard，/land-and-deploy 在 PR 合并后通过金丝雀检查验证生产健康。Reflect：/retro 做周度工程回顾（按人拆分贡献），/document-release 自动更新所有文档，/learn 管理跨会话的项目知识。

/qa：质量保障——系统化 QA 测试 web 应用，然后逐个修复发现的 bug——每个修复原子提交，修完重新验证。三个级别：Quick（只查关键/高优）、Standard（+中优）、Exhaustive（+外观）。 /canary：部署后金丝雀监控——使用 browse daemon 持续监控线上应用——控制台错误、性能回退、页面故障。 /benchmark：性能基准测试——页面加载时间、Core Web Vitals、资源大小的基线和对比。回退阈值：>50% 或 >500ms = REGRESSION，>20% = WARNING。 /ship：发布工作流——检测+合并基础分支→跑测试→审查 diff→版本号 bump→更新 CHANGELOG→提交→推送→创建 PR。在创建 PR 前会显示一个「Review Readiness Dashboard」。 /retro：周度工程回顾——分析提交历史、工作模式和代码质量指标。团队感知——按人拆分贡献，给出表扬和成长方向。

SAFETY NET

安全是前置而非后置——在命令执行前拦截，不是事后检查

/careful 通过 PreToolUse hook 在 Claude 执行 Bash 命令之前自动拦截破坏性命令（rm -rf、DROP TABLE、force-push、git reset --hard），用户可以覆盖。/freeze 限制文件编辑到特定目录，/guard 是最大安全模式（careful + freeze）。/context-save 和 /context-restore 让你保存和恢复工作上下文，不再从零开始。

gstack 的设计哲学归结为 7 条信念：Skill 是第一等公民、Sprint 有顺序、铁律优于建议、多视角优于单视角、原子操作优于批量、品味不可自动化（autoplan 在品味决策时一定停下来问人）、安全是前置而非后置。

/careful：安全护栏——在执行破坏性命令前发出警告：rm -rf、DROP TABLE、force-push、git reset --hard、kubectl delete。用户可以覆盖。通过 PreToolUse hook 实现——在 Claude 执行 Bash 命令之前自动检查。 /freeze + /unfreeze：目录锁定——限制文件编辑到特定目录。在会话期间，Edit 和 Write 操作在允许路径之外会被阻止。 /guard：最大安全模式——combine /careful + /freeze。碰生产环境或调试线上系统时用。 /context-save + /context-restore：上下文持久化——保存工作上下文（git 状态、已做决策、剩余工作），让任何未来会话都能无缝接续。不再从零开始。 gstack 的深层信念： 1. Skill 是第一等公民。 2. Sprint 有顺序。 3. 铁律优于建议。 4. 多视角优于单视角。 5. 原子操作优于批量操作。 6. 品味不可自动化。 7. 安全是前置而非后置。

CEO + ENG REVIEW

CEO 模式有四种范围决策——从「全部推翻重来」到「范围刚好」

/plan-ceo-review 像创始人一样审视你的计划。它有四种模式：SCOPE EXPANSION（计划太保守了，放大它）、SELECTIVE EXPANSION（大部分 OK 但某些方面需要扩展）、HOLD SCOPE（范围刚好）、SCOPE REDUCTION（太多了，聚焦）。16 种认知模式加持，9 条核心原则中最关键的是：允许说「全部推翻重来」。

/plan-eng-review 则是工程经理视角——锁定架构、数据流、边界情况、测试覆盖率和性能。它的特点是每个问题都带有观点明确的建议，不是「你怎么想？」而是「我建议 X 因为 Y，你同意吗？」，因为模糊的问题只会浪费决策者的时间。

DESIGN + DX + AUTOPLAN

设计评分 0-10，DX 三种模式，autoplan 一键全跑

/plan-design-review 对每个设计维度打 0-10 分，不只是打分——它会解释怎样才能达到 10 分，然后直接修改计划去接近那个标准。/plan-devex-review 专门为面向开发者的产品设计（API、CLI、SDK、文档），有三种模式：DX EXPANSION（扩大开发者体验范围）、DX POLISH（精细打磨）、DX TRIAGE（紧急分诊）。
