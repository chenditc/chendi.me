第二幕

人 ≠ Agent

04 / 人的局限

人类社会有组织架构，是因为
每个人都有上限

精力有限、知识有限、注意力有限、能力有限。分工协作，是人类补偿个体局限性的方式。

人类能力上限
精力 25%
知识 35%
注意力 20%
能力 40%

所以一个人做不完的事，拆给一个团队。一个团队做不完的事，拆给一个组织。

05 / Agent 的能力

但 Agent 的精力、知识和处理能力
远超人类

用人类的组织架构思维去限制 Agent，大概率无法发挥它的全部潜力。

第三幕

三个合理的理由

07 / 原因一

上下文窗口装不下了

目前模型的上下文窗口仍然有限。当面对一个巨大的任务时，单个 Agent 的上下文可能会被撑满。为了不影响交付质量，我们将其拆分成多个 Agent，每个 Agent 负责一部分。

上下文使用量0%
上下文使用量48%
上下文使用量52%

这是一个物理层面的限制，而不是设计偏好。当上下文装不下时，拆分是合理的。

深入了解 ↓

08 / 原因二

自己审自己，永远有偏见

Agent 在评估自己工作时往往存在偏见。我们经常将「代码审核者」和「测试者」分开，就是为了避免既当运动员又当裁判员的情况。

🔨构建者
📄
v1 ❌ v2 ⚠️ v3 ✅
🔍评审者

分离构建者和评审者，让独立的视角来保证质量。这种拆分是为了客观性，不是为了分工。

深入了解 ↓

09 / 原因三

一个角色名，压缩了一整套指令

当你告诉 Agent「你是一个测试者」时，它立刻就能领会对待代码应有的态度和立场，而不需要你花篇幅去解释。角色设定本身就是一种高效的信息压缩。

检查语法错误
验证边界条件
确保覆盖率
测试异常路径
检查性能瓶颈
验证安全漏洞
回归测试
写测试报告
🏷️ 测试者

这不是为了分工，而是为了让 prompt 更简洁、更高效。
